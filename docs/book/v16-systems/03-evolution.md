# How brain Grew

*What does the history of one real engine teach about how machine learning systems evolve?*

Copy a function of thirty lines into the second model of an engine, because the second model needs nearly the same thing and a copy is quicker than deciding where a shared version should live. Copy it again for the third model, and for every model after that. Suppose that the function then needs one fix for every model that arrives, and that whoever makes a fix finds and repairs every copy except, one time in twenty, one of them. When the fortieth model has arrived and its fix has landed, 820 edits have been spent on applying fixes, and on average about 23 of the 40 copies have missed at least one of them: more than half of the engine runs a version of the function that nobody wrote on purpose. Had the copies been gathered into one shared function on the arrival of the second model, the same forty fixes would have cost 42 edits, and no copy would exist to drift.

The arithmetic is not peculiar to machine learning. Lehman (1980) stated it as two laws of programs in use: such a program must keep changing or become less useful, and as it changes its complexity grows unless work is spent to reduce it. What machine learning adds is that drift is quiet. A copy of a normalization or an embedding that has missed a fix still returns numbers of the right shape and the right size, and the model still trains or still generates something plausible; Sculley and colleagues (2015) catalogued the maintenance costs that are specific to machine learning systems, among them entanglement between components, glue code and dead experimental code paths. The questions worth asking of a real engine are therefore empirical. In what order does it acquire the parts of a complete system? Which of its first decisions survive, and which are reversed once the work grows? What breaks as more models arrive, and what kind of change repairs it for good rather than once? The history of brain, kept as a linear sequence of commits with their messages, answers these questions for one engine, and the answers below are read from the commits and checked against the code they left.

Five earlier ideas carry the reading. Chapter 2 ("Capstone: From Raw Data to a Served Model") built a complete path: name its stages in order, say what each stage hands to the next, and say what the whole path is compared with. Chapter 1 ("The Architecture of a Machine Learning Engine") allowed three ways of reaching a behaviour that lives somewhere else; which three, and which way does it forbid? A set of defects shares one mechanism and one hiding place: what does Volume XV, Chapter 5 ("A Catalogue of Expensive Mistakes") call such a set, and why does one check placed outside the hiding place catch all of its members while a hundred checks inside it catch none? A test sums the counts of every kernel whose name equals one string, and the kernel is renamed: the test still passes, so what kind of gate has it become (Volume XV, Chapter 2, "Testing Numerical Code")? And reaching further back, how many floating-point operations (FLOPs) does the product of an $m \times r$ matrix with an $r \times n$ matrix take when a multiply and an add are counted separately (Volume IV, Chapter 3, "Memory Bandwidth, Compute and the Roofline")?

## A single program of shaders, cut into a workspace

The first commit with code in it, commit `1fa53524c` (23 June 2026), is one program: a small sparse mixture-of-experts (MoE) language model, a network whose feed-forward part is several "experts" of which a router chooses a few for each token, reimplemented from a Python training script as a pipeline of compute kernels written in the WebGPU Shading Language (WGSL). Its README describes the choices it made for that one model. Every stage of the forward pass is its own hand-written kernel; arithmetic is 32-bit floating point only; each kernel uses only the core features every compute device offers (one group of bindings, at most four storage buffers, no atomic operations, no subgroup operations, no 16-bit floats), so that the same program runs on old graphics processors and on new ones. The Python script was committed beside it moments later and left the repository the next day, in commit `c0f33b300` (24 June 2026), whose message says the reference scripts would be kept outside the repository "as porting source-of-truth, not as a build/test dependency".

Commit `d9bfa70d4`, the same day, cut the program into a workspace of separate packages ("crates") under `crates/`. Its message lists what each part was for: `kernels`, holding all the WGSL as constants ("the source of truth"); `gpu-core` for the device, dispatch and buffers; `paramstore` for the parameter, gradient and optimizer buffers; `optim` for the AdamW update and gradient clipping; `checkpoint` for the weights container; two models, the mixture of experts and a small control model; an optional path for one native graphics interface; a demonstration that ran in a web browser; and two packages, `autodiff` and `timeseries`, described as "placeholders for later phases". The split came when there was already a second model and a second build target, the browser, and the code it moved shows why: every place where the program had included a shader file now named one constant in `kernels`, so the browser build and the native build could not read two different copies of a kernel.

Some of what was decided on that day still stands, and it is worth seeing which part. The repository's rules today (`AGENTS.md`) say that WGSL is the source of truth and the reference provider, that kernels live only in `crates/kernels/wgsl/`, and that they stay within the core features: 32-bit arithmetic, at most 8 storage buffers, no atomics. The limit on storage buffers has doubled since the first program; the rest is the first program's decision, written down as a rule. What has not survived is the other kind of decision made that day: the two placeholders, which were predictions about where future work would live, and both were later deleted. The difference between the two kinds is the first lesson of the history. A decision about meaning (one source for every kernel, one numeric format for the reference) cost nothing to keep as the engine grew and gave every new device one reference to be compared with. A decision about the future shape of the work was a guess, and the work went elsewhere.

The middle of the path came first. On day 0 the engine had kernels, a device layer, a model, an optimizer, a weights format, a data layer (commit `00121704e`: tokenizers, synthetic dataset generators and loaders) and the gradient check (commit `afbbae41d`, whose message calls it a "numerical backprop correctness gate" that replaces a comparison with an external framework). On day 20 the device layer was cut into one crate per backend behind a small set of traits, and commit `7c8c97045` records why no model had to change: the type the models call, `Gpu`, kept its public interface and became a thin facade over whichever backend is selected. The front doors came a month after the split: one interface through which every model advertises its actions on day 32 (commit `da5bdf257`, "instead of bespoke per-model CLI subcommands", that is, separate command-line commands for each model), and the layer that speaks the hypertext transfer protocol (HTTP) on day 37. The rows from day 50 on are a different kind of part. They are not new stages of the path; they are single answers to questions that several parts had been answering separately. The registry of day 50 says so in its message: the engine had "four separate, drifting answers to 'which architecture is this'". The catalog of day 62 lets a program enumerate the served models without going through a command line, a message bus or HTTP. The serving library of day 100 moved the code that tells a scheduler how much memory each model needs out of the command-line program, because "a binary cannot be linked", so no other process could serve a model under a budget. And the batching loop of day 114 is, in its own words, an extraction of "the copied run_batch_scheduled loops" of three language models into one crate generic over the decoder.

That shape is the general one. **System evolution** is the sequence of changes by which a long-lived system's structure is reshaped by the work it is asked to do: arrangements made for its first workload (sizes, names, copies, placeholders, judgements of what is negligible) meet later workloads, and each is then generalised, gathered into one home, guarded by a check that covers the whole class of its failures, or deleted. The record of those changes, read with the code they left, is evidence of which decisions held. In brain the server a beginner might build first was not first; the parts that make one model work were first, and the shared answers came once several models existed and their separate answers had begun to disagree. A shared answer is rarely designed before the second answer exists, and the cost of that order shows in the judgements, capacities, copies and names that the engine later had to revisit.

## A judgement that carried its workload's numbers

The first program's README contains a sentence that is worth reading slowly. Training dropped tokens that exceeded an expert's capacity; inference, it says, "evaluates all experts and masks each by the renormalised top-k gate", which is numerically identical to running only the selected experts, and that at `n_experts=4, top_k=2` the cost, twice the expert FLOPs of a true sparse dispatch, "is negligible here". Both halves are true. Multiplying an expert's output by a gate of exactly zero adds exactly zero, so the dense result equals the sparse one; and with 4 experts of which 2 are selected, computing all 4 costs twice what computing 2 does. The judgement, though, is a statement about two numbers, and the numbers belong to that model.

The cost of one expert is easy to count. An expert of the kind these models use is a gated feed-forward block with three weight matrices, two that map the model's width $d$ to the expert's hidden width $h$ and one that maps back, so one token costs $3dh$ multiply-adds, or $6dh$ FLOPs counting a multiply and an add separately (the rule of the matrix product in Volume IV, Chapter 3). Dense evaluation runs all $E$ experts on every token and sparse dispatch runs the $k$ that the router selects, so their ratio is $E/k$ whatever $d$ and $h$ are. The table applies the count to the first model and to two configurations the engine supports now.

For the first model dense evaluation costs 196,608 FLOPs of expert arithmetic per token where 98,304 would do, a factor of 2. For the 128-expert decoder the factor is 16, and the wasted part, about $1.13 \times 10^9$ FLOPs per token and layer, is more than the whole expert work of the first model by a factor of several thousand. For the 256-expert configuration it is 32. Nothing about the code changed between the rows; only the two numbers the judgement rested on did. Commit `0976631bf` (7 August 2026) is the moment the engine re-derived it. Its message describes the one model that then imported a published mixture of experts as evaluating "every expert densely over the whole row batch", gives the cost for a 128-expert, top-8 router as 16 times that of a real top-$k$ dispatch, and adds a shared sparse forward in `crates/model/src/moe.rs` with one new kernel, `crates/kernels/wgsl/moe_linear_gated.wgsl`: a matrix product that skips, before its inner reduction, every row whose gate for this expert is zero, so that the FLOPs of a row not routed to an expert are never spent rather than spent and multiplied by zero. It was checked against a dense oracle built from the existing kernels, on all three backends, to an absolute difference below $10^{-5}$.

The lesson is not that the first judgement was careless. It was exact for its workload, and it stated its workload, which is what made the later correction easy to see. The habit to keep is to record a judgement of cost together with the numbers it was made at ("$E/k = 2$, negligible here"), so that whoever adds a model with other numbers can see that the judgement no longer covers it. The last column of the table points at a second decision of the same day, one that did not state its numbers.

## A capacity that each new model found again

The router of the first program chooses, for every token, the $k$ experts with the largest scores and renormalizes their probabilities. Its kernel, `crates/kernels/wgsl/router_gate.wgsl`, kept the probabilities of one token and a flag per expert ("already chosen") in two arrays local to the invocation, and WGSL needs the length of such an array as a literal. The first version, in the workspace split, declared `const MAX_EXPERTS: u32 = 64u;`, wrote `var prob: array<f32, 64>;` and `var used: array<bool, 64>;`, and noted that the number of experts "is assumed <= MAX_EXPERTS". For a model of 4 experts, 64 slots is room to spare. For the 128 and 256 experts of the table it is not, and WGSL does not make an index past the end of a local array an error the program can see: the access is left to the implementation, which may clamp or discard it, and knowledge #35b records that it showed as silently wrong probabilities for the upper experts, not as a crash.

What happened next is the clearest case in brain's history of a defect class meeting a growing system, and it took four commits to close.

1. Commit `0976631bf` (7 August 2026), the sparse forward of the previous section, raised `MAX_EXPERTS` from 64 to 128 for the 128-expert decoder. The two arrays kept their own literal, 64.
2. Commit `e3019d191`, later the same day, found it. Its message records why nothing had: the existing parity test of the sparse path used 8 experts, and the defect surfaced with the 128-expert decoder, the first real model to run the kernel above 64; knowledge #35b adds that the decoder had been compared, end to end, with the expert choices and weights of the published model. The commit raised both arrays to 128.
3. The router's backward kernel, `crates/kernels/wgsl/router_bwd.wgsl`, had scratch arrays of its own, also of 64, and two days later a model with 256 experts reached the forward's new limit of 128. Commit `7fbbfce60` (9 August 2026) rewrote the backward kernel without any array sized by the number of experts, and commit `595d1ad72` the same day did the same for the forward and its training variant. The probability of each expert is kept in the output buffer the kernel already owns, whose size is set by the caller to rows times experts, and the only local array left holds the indices of the experts already chosen, so its length is set by the number of experts a token selects (at most 32 in the kernel), never by the number of experts.
4. A third router kernel, the sigmoid-scored router with group-limited selection in `crates/kernels/wgsl/router_gate_sigmoid.wgsl`, had its own copy of the same scratch arrays, still at 64, and the model that needed it, the 256-expert configuration of the table, carried a refusal in its constructor rather than build wrongly. Commit `3037848de` (2 September 2026) rewrote that kernel in the same array-free way, removed the refusal, and renamed the one bound that remains, on the number of expert groups, so that the array it sizes names what it counts.

The class is "a local array sized by a constant chosen for the first workload". Its hiding place is any test whose sizes are below the constant, which is to say every test written while the constant was generous, and a second hiding place sat beside it: the existing test compared the sparse path with a dense path built from the same kernels, and a defect present in both sides of a comparison cancels out of it. Every step in the list was prompted by a model that left the first hiding place. The fix that closed the class for good was not the one that came first. Raising the constant moved the boundary to where the next model would find it; removing every array whose length depends on the number of experts left nothing for a larger model to overrun. The gates written with the fix leave both hiding places at once. `crates/model/tests/it/router_gate_expert_cap.rs` compares the kernel with a host oracle that re-derives the selection independently (a softmax, then a greedy choice of the largest without replacement, then renormalization) at 8, 129 and 256 experts: below the old boundary, one past the second one, and far past both. Beside it, `router_bwd_expert_cap.rs` runs the backward kernel at 8, 65 and 128 experts and `router_gate_sigmoid_expert_cap.rs` the sigmoid router at 8, 65 and 256, 65 being the first count the old arrays of 64 could not hold; both compare the device with a host program that follows the kernel's passes step by step, which is not the kernel's own composition of device kernels and so does not share a device defect.

The difference between moving a boundary and removing it can be counted. Suppose the code that carries a class exists in several copies, as the scratch-array shape did in several router kernels, and every new model meets the class in each copy with some small chance that the existing tests miss. An instance fix repairs the case that escaped and leaves the class open; a class fix closes it in the code it is applied to.

The three columns are three formulas. With $K_{\mathrm{c}}$ copies, a chance $q_{\mathrm{esc}}$ per copy and model, and $M$ new models, instance fixes leave every copy open, so the expected number of escapes is $K_{\mathrm{c}} M q_{\mathrm{esc}}$, which grows without bound: 32.00 after 80 models. A class fix in each copy closes that copy at its own first escape; a copy is closed after $M$ models with probability $1 - (1 - q_{\mathrm{esc}})^M$, and it escapes at most once, so the expectation is $K_{\mathrm{c}}\left(1 - (1 - q_{\mathrm{esc}})^M\right)$, which approaches $K_{\mathrm{c}} = 4$ (3.999 after 80). One shared implementation that serves all the uses is met by a model with probability $1 - (1 - q_{\mathrm{esc}})^{K_{\mathrm{c}}} = 0.3439$ and closed by its first escape anywhere, so it escapes at most once and, writing $p_{\mathrm{sh}} = 0.3439$, its expectation after $M$ models is $1 - (1 - p_{\mathrm{sh}})^M$, which approaches 1. A class fix turns a line into a ceiling; copies multiply the ceiling. The figure draws the three curves.

The router's history has both effects in it. Raising the constant was an instance fix, and the next larger model found the class again. Every kernel that had copied the scratch-array shape needed its own repair, and the message of commit `595d1ad72` says of the one kernel it left that it was "untouched and still behind its documented" refusal, which the commit of 2 September then removed; the record of knowledge #35b puts the general point in one sentence: fixing the first two instances "did not imply the third and fourth were safe".

## Copies gathered into one home

The opening's two numbers, 820 edits and about 23 drifted copies, come from a model of copies and fixes that can be stated exactly, and stating it shows what a late hoist (gathering the copies into one shared implementation) actually costs. Models arrive one per period, in periods $1, \dots, N_{\mathrm{m}}$. In each period the model arrives first, and then $f_{\mathrm{fix}}$ fixes of the shared component land. Before the hoist each model has its own copy, made from an up-to-date one, and a fix must be applied to every copy that exists; each application is forgotten with probability $\mu_{\mathrm{miss}}$, independently of every other. A copy that has missed any fix is drifted. The hoist happens on the arrival of model $k_{\mathrm{h}}$, before that period's fixes: one copy becomes the shared implementation, each of the $k_{\mathrm{h}}$ models so far is pointed at it with one edit, and every drifted copy has to be reconciled with it, which changes the numbers that model produces. After the hoist, a fix is one edit.

Copy $i$, made when model $i$ arrived, has seen the fixes of periods $i, \dots, k_{\mathrm{h}} - 1$ by the time model $k_{\mathrm{h}}$ arrives, $(k_{\mathrm{h}} - i) f_{\mathrm{fix}}$ of them, and has missed none with probability $(1 - \mu_{\mathrm{miss}})^{(k_{\mathrm{h}} - i) f_{\mathrm{fix}}}$. The expected number of drifted copies at the hoist is the sum over the copies of the chance that each has drifted, and the edits are those spent on fixes before the hoist, one per copy and fix, plus one per fix after it, plus the migration:

$$D(k_{\mathrm{h}}) = \sum_{i=1}^{k_{\mathrm{h}}} \left(1 - (1 - \mu_{\mathrm{miss}})^{(k_{\mathrm{h}} - i) f_{\mathrm{fix}}}\right), \qquad E_{\mathrm{fix}}(k_{\mathrm{h}}) = f_{\mathrm{fix}} \sum_{t=1}^{k_{\mathrm{h}} - 1} t + f_{\mathrm{fix}} (N_{\mathrm{m}} - k_{\mathrm{h}} + 1).$$

```text
function drifted_at(k: int, f: int, mu: real) -> real:
    require k >= 1 and f >= 0 and 0 <= mu and mu <= 1
    total = 0.0
    for i in 1 ..= k:                        # copy i was made when model i arrived
        total = total + (1 - (1 - mu) ^ ((k - i) * f))
    return total

function hoist_edits(n: int, k: int, f: int) -> int:
    require 2 <= k and k <= n and f >= 0
    edits = 0
    for t in 1 .. k:                         # periods before the hoist: t copies receive each fix
        edits = edits + f * t
    edits = edits + f * (n - k + 1)          # periods k .. n: one edit per fix
    return edits + k                         # and one migration edit per model so far
```

Without any hoist the edits are $f_{\mathrm{fix}} N_{\mathrm{m}}(N_{\mathrm{m}} + 1)/2$, and the drifted copies after the last period's fixes are the same sum with $N_{\mathrm{m}} - i + 1$ fixes seen by copy $i$.

The common advice runs the other way: wait for the third occurrence before abstracting, the "rule of three" that Fowler (1999) attributes to Don Roberts, so that the shared form is designed from enough examples to see what varies. The model does not contradict the advice so much as locate its price, and brain's history shows the price being avoided rather than paid. The hoist does not need to know in advance what will vary, if what varies becomes a parameter when it appears.

Commit `fbf640526` (4 August 2026) is the plainest case. A shared sinusoidal timestep embedding (the vector of sines and cosines of a diffusion step that conditions a denoiser) already existed in `crates/model/src/hostmath.rs`, and the message records that the work on a new image model, an image-generating UNet, had grown a second copy, on the argument that two of its conventions were "diffusers conventions, not general math". The commit moved the two conventions onto the shared function as parameters instead: `flip_sin_to_cos`, which chooses whether the cosine half or the sine half comes first, and `downscale_freq_shift`, which sits in the denominator of every frequency, $\omega_j = P^{-j/(n_{\mathrm{half}} - s)}$ for $j = 0, \dots, n_{\mathrm{half}} - 1$, where $n_{\mathrm{half}}$ is half the embedding's length, $P$ its maximum period and $s$ the shift, so that it moves every frequency rather than one. The UNet's forward pass entered the history a minute later, in commit `c7d97a708`, calling the shared function; no copy of it was ever committed. The hoist kept the arithmetic the same (the angle accumulated in 64-bit floating point and rounded once), and its message reports identical parity digits before and after. It also left a third copy alone on purpose, because that copy accumulated in 32-bit floating point and pointing it at the shared function would have moved a number its parity gate checks: exactly the fifth column of the table, a drifted copy whose reconciliation is a separate change with its own re-check. Seventeen days later the knobs paid for themselves. Commit `3fa5471e4` (21 August 2026) brought the flow decoder of a speech model in `crates/cosyvoice/src/flow.rs`, whose reference orders the halves sine first and shifts the denominator by 1, and it calls the shared function with `false` and `1.0` where the image models of the hoist pass `true` and `0.0`; no copy was written for a convention that did not exist when the parameters were made.

The router's backward pass was hoisted the same way. Commit `7fbbfce60` describes two complete, gradient-checked mixture-of-experts backwards that already existed, one in the training loop of the first model and one in a later decoder with the sigmoid-scored router, and says that comparing them line for line showed the expert half identical and only the router half different. The shared code it created in `crates/model/src/moe.rs` has one entry point for the router's backward, `router_bwd`, selected by a `RouterKind` with one variant for each of the two routers, and one expert backward for both. The batching loop of day 114 in the earlier table is a third instance: three copied scheduling loops became one crate, `crates/llmserve`, generic over the decoder, with the differences between the models (how a prompt is parsed, how adapters are routed, how a rejection is worded) behind a seam of their own.

A hoist, read this way, is a diff of the copies. What is identical becomes the shared implementation; what differs on purpose becomes a parameter or a variant, named for what it means; and what differs by accident, because one copy missed a fix or rounded differently, is a behaviour change to be made and re-checked on its own. The later the hoist, the larger the third part.

## Names chosen for the first member of a kind

A name given while a system has one member of some kind tends to be the name of the kind. The first model's package was called `moe`, after the idea it embodied, and for six weeks that was unambiguous. By August the engine had real mixture-of-experts decoders, and the shared routing arithmetic they were built on lived in a module called `model::moe`. Commit `a126e9b22` (13 August 2026) renamed the engine's four own small models, those with no published reference to check against, to `toymoe`, `toypid`, `toyseq2seq` and `toyautoencoder`. Their rows in the architecture registry `crates/arch/src/lib.rs`, added earlier the same day, mark them `Source::Toy`, which keeps them gradient-checked and benchmarked like any architecture while leaving them out of the listings a user reads. The rename is instructive in how it was checked. A text substitution of `moe::` by `toymoe::` cannot tell a reference to the crate from a path into the shared module, so the substitution skipped every `moe::` preceded by `model::` or `crate::`; one model imported the module with the idiom that brings it into scope under its bare name, so its own calls read `moe::` with nothing before them, and those were found, as the message records, "only by the resulting" compile error. Text search proposes a rename; the compiler checks it.

A name can also outlive what it names inside one part. A shared block of attention code kept, in a structure of kernel slots, a field called `matmul_reg2`, after the tiled matrix-multiply kernel that filled it. A later kernel computed the same products in the same order of accumulation with fewer shared-memory conflicts, and commit `9b6415a6c` (5 August 2026) moved every model that still selected the older one onto it. It also renamed the field `matmul_reg`, because, in the message's words, "the field means 'the tiled GEMM slot'" (GEMM, a general matrix multiply), "and naming it after one particular kernel is what made the wrong choice look deliberate at every call site". The same commit found a gate that the move had silently emptied: a test that bounded a model's multiply-add volume summed the counts of the kernels named `matmul` and `matmul_reg2`, the model had already moved to the newer kernel, so the filter matched nothing for the tiled kernel and the bound compared against an undercount. The commit pointed the filter at the kernel the model dispatches. That is the gate of Volume XV, Chapter 2 that never runs, produced by evolution rather than by a mistake on the day the test was written: the test was right when written, and a change of kernel elsewhere took its subject away. A name is a reference, and every reference to a name is a place a rename must reach.

## A list that outgrew the code that counted it

Machine learning engines grow along a few axes over and over: more architectures, more devices, more numeric formats. Code that enumerates the members of such a set is correct on the day it is written and wrong on the day the set grows, unless the enumeration is derived from the set itself.

The engine's list of element formats, the enum `DType` in `crates/backend-api/src/lib.rs`, had seven members when a per-device table was first sized from it: 32-bit, 16-bit and bfloat16 floating point, 8-bit integers and three packed 4-bit and 8-bit quantized formats. A description of each device's arithmetic, `ArchDesc` in `crates/backend-api/src/arch.rs`, kept one slot per format in an array whose length was a constant written by hand, `const DTYPE_COUNT: usize = 7`, indexed by converting the format to an integer with a cast that accepts any value. The comment above the constant said that a new format "only ever needs a new match arm plus incrementing this constant, never a silent array-bounds trap", and pointed at the test that would catch a forgotten increment. The list then grew to eleven, with 4-bit NormalFloat (NF4), 4-bit floating point (FP4) and two 8-bit floating-point (FP8) formats, and the constant did not. The test, `every_dtype_round_trips_its_own_tier`, enumerated a hard-coded list of the original seven and compared its length with the constant, so it compared a copy with a copy and kept passing; a query for one of the four new formats would have indexed past the end of the array and stopped the program. Commit `61a4315c0` (1 October 2026) replaced the copies with the set. `DType::ALL` is now the one list of the formats in declaration order; `DType::index` is a `match` over every variant, which the compiler requires to be exhaustive, so a new variant does not compile until it has an index; the tier array is sized `DType::ALL.len()`; the test iterates `DType::ALL`; and a second test, `all_lists_every_dtype_at_its_own_index`, checks that every entry of the list sits at its own index.

Since then the set has grown again. Commit `b77501bc5` (10 November 2026) added three rotated-codebook weight formats, `Cq2`, `Cq3` and `Cq4`, extending the list and the match in `crates/backend-api/src/lib.rs` to 14 formats, and it did not touch `crates/backend-api/src/arch.rs` at all: the table grew with the list it is sized from. The same class appears in the router story, where `MAX_EXPERTS` and the two array literals were three places holding one number, and the remedy there was the same in spirit: make the size follow from the thing it measures, or remove the size.

## Rules brought into a system that is already large

A rule adopted on the first day costs nothing; the same rule adopted months later, against code that already breaks it in many files, is either all of those edits made at once or a rule nobody enforces. brain's gates bring such rules in as ratchets. The first, `scripts/gates/ratchet.py`, arrived with commit `4a18f6916` (20 October 2026) to stop production loaders from turning a quantized checkpoint into a whole 32-bit tensor in memory. It counts, for every production source file, the lines that match a set of patterns (the call forms that return a whole tensor as 32-bit floats), and compares each count with an allowlist of `path`, `count` and `reason`.

```text
function ratchet_problems(actual: map<text, int>, allowed: map<text, int>) -> list<text>:
    problems = []
    for path in keys(actual):
        if actual[path] > get(allowed, path, 0):
            append concat("NEW: ", path) to problems     # a new violation: fix the design
    for path in keys(allowed):
        if allowed[path] > get(actual, path, 0):
            append concat("STALE: ", path) to problems   # the code improved: lower the entry
    return problems
```

The gate passes only when `ratchet_problems` returns an empty list. The first loop is the rule: no file may get worse. The second is what makes it a ratchet and not a list of exceptions: when a migration removes a call, the gate fails until the entry is lowered or deleted in the same commit, so the allowance can only shrink and can never quietly cover a new call in a file that once had an old one. The header of `scripts/gates/check-whole-tensor-loads.sh` states the policy beside the patterns: "a new call is a design defect, not an allowlist addition". The allowlist has shrunk since; commit `d1119732b` (14 November 2026), for one, moved a small model's load out of the command line into its own crate with half the matching calls and lowered another file's entry from 4 to 2. Later gates are built on the same helper (`check-model-flags.sh`, `check-format-logic.sh`, `check-placement-accounting.sh` and `check-adapter-naming.sh` beside it in `scripts/gates/`), and each could be enforced from the day it was written, against a tree that did not yet obey it.

The record of what went wrong evolved under the same pressures as the code. The lessons the engine learned were kept in one file, which by September had grown to more than five thousand lines. Commit `8487d8eb6` (22 September 2026) split it into one file per finding under `.agents/knowledge/`, kept each finding's number as its permanent citation key ("ids are never reused and never renumbered"), and added an index generated by `scripts/build/gen-knowledge-index.py`. The message reports why the generator also checks that no two findings claim one number: two numbers had already appeared twice in the single file, so a citation of either resolved to whichever finding a reader happened to find first. The check runs as `make check/generated/knowledge-index`. The knowledge base is thus held to the rules the engine holds its code to: one place for each fact, a derived listing rather than a maintained one, and a gate that fails when the two part company.

## What the first plan predicted, and what growth deleted

The workspace split of day 0 created two packages for work that did not exist yet. `autodiff` was to hold automatic differentiation, a general mechanism that derives a backward pass from a forward one. It never did: every model came to carry a hand-written backward that the finite-difference check of day 0 validates (Volume III, Chapter 4 tells why the engine works this way), and commit `6eee2197d` (1 September 2026) deleted the placeholder after checking that nothing in the workspace referred to it, noting that the claim it once carried, a mechanism "reused by every model", "was never true". `timeseries` was to hold a time-series model. That work arrived too, in other places: the windowing, splits, baselines and scaling it promised live, according to commit `e9a2718c0` (12 November 2026), in `crates/forecast`, in `crates/fcbench` and in each forecasting model's preprocessing, and that commit removed the six-line package together with its entry in the map of layers.

A placeholder is a prediction about where a capability will be implemented, written before the capability's shape is known. Both of these were wrong in the same way: the capability was real, and it was built where the work that needed it was, not where the plan expected it. Keeping a placeholder has a cost beyond its few lines. It is a package that every build compiles, that the layering rules must place, and whose name tells a reader that a mechanism exists, or is about to, where nothing is. Deletion is ordinary maintenance in a growing system: the batching hoist of day 114 removed more lines from the three language models than it added to the shared crate, because each lost its own copy of the scheduling loop, and the placeholders went the same way once it was clear where their work lived. A system that only ever adds is carrying its own history as dead weight.

## Summary

The history of brain shows a machine learning engine growing outward from the middle of its path. On the first day it had kernels, a device layer, a model, an optimizer, a weights format, data and a gradient check; the doors through which people reach it came a month later, the shared answers that many parts read (a registry, a catalog, a scheduler's knowledge of memory, one batching loop) came once several parts had been answering separately, and a library facade and a measured quantization search came last. **System evolution** names that process: arrangements made for the first workload meet later workloads, and each is generalised, gathered into one home, guarded by a check that covers its whole class, or deleted.

Four mechanisms recur. A judgement of cost is true at its workload's numbers: dense evaluation of the experts cost a factor $E/k = 2$ for the first model and 16 and 32 for the later ones, and the correction followed once someone redid the arithmetic. A capacity chosen for the first workload is a defect class whose hiding place is every test written while the capacity was generous: the router's fixed scratch arrays were outgrown four times, in three kernels, and only removing every array sized by the number of experts closed the class; in the model of the class-closing table, instance fixes leave the expected escapes rising in a straight line, a class fix bounds them by the number of copies, and one implementation bounds them by 1. Copies drift, and a late hoist pays for every drifted copy as a behaviour change to re-check (about 7 expected at the twentieth model in the copies table, where a hoist on the arrival of the second model leaves 0.05); the engine's hoists avoided the price by turning each real difference into a parameter as it appeared. And names, lists and placeholders written for the first member of a kind go stale as the kind grows, unless they are derived from the set they describe or removed.

The models of the two tables rest on stated assumptions (independent misses, a fixed chance per model) and show the shape of the costs, not their size in any real project; the dates and decisions come from commits and are confirmed against the code. This volume has now built an engine's architecture, the complete path through it and the record of how one such engine came to be.
