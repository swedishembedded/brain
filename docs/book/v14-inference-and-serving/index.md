# Volume XIV: Inference Engines and Production Serving

A trained model is a file, and a file answers nobody. Between the file and a person waiting for a reply stands a program that has to get gigabytes of weights from a disk onto a device, decide which of several models may occupy which memory, keep the caches of many conversations from crowding one another out, share one device among requests that arrive when they like, and do all of it for clients that are not all friendly. Each of those is a problem of its own, and each is a problem of bytes before it is a problem of arithmetic: a model that fits on a device when it is alone does not fit beside another, a conversation's cache grows with every word it reads, and a request that costs the server more than it costs the sender is a weakness and not a feature.

The volume follows a model from the moment it is named to the moment a server stops. It starts with loading: how a name becomes a file, how a file reaches a device without ever existing in memory more than once, and how a quantized tensor is moved in the form it is stored in. It turns to memory, first the budget that decides which models live on which device when they do not all fit, then the cache of keys and values that every conversation owns, which can be paged, shared between conversations that begin alike, stored in fewer bits and moved to a slower tier. It takes up the schedule that keeps a device busy while many users wait, with batches that change as requests start and finish and prompts that are cut into pieces so that one long prompt does not stall the rest, and the admission rule that turns away what the device cannot hold. It shows how a small model's guesses can make a large model's generation faster without changing what it says, how an engine with hundreds of models presents them through a few stable interfaces, what a hostile request or a malicious model file can do to a server and how the bounds are set, and how a running engine is observed, controlled and shut down cleanly.

The volume leans on the ones before it, and on three of them most. Volume IV supplied the number formats, the roofline and the quantized block formats whose bytes a loader has to move, and the cost model that says a step of generation is limited by the bytes it reads. Volume V supplied the decoder, the cache of keys and values and the two phases of generation that a server has to schedule. Volume VI supplied the checkpoint formats and the discipline of proving a loaded model equal to its reference, which is what makes it safe to say that a faster way of loading is the same model. Volume XIII is the neighbour on the other side: training leaves a checkpoint that is complete and verifiable, and the first question of this volume is what happens when a process opens it.

The order follows what each part needs of the one before. Nothing can be budgeted until the bytes of a model are known and loadable, so loading comes first and the memory chapters after it. The cache of a conversation is the part of memory that grows while a server runs, so it follows the budget of the models; scheduling follows the cache because a scheduler admits a request only if its cache will fit. Speculative decoding changes how many tokens one pass of the large model produces and so leans on the phases the scheduler already treats separately. The interface chapter comes once the engine has things to expose, security once it has an interface to attack, and operations last among the methods, since observing and stopping an engine presupposes everything that it runs. The volume ends with a project that builds a server for several clients at once within a fixed memory.

You can state how many copies of a model's weights a loader holds and why, read a range of a stored tensor without decoding the rest, work out the size and the byte ranges of a quantized tensor from its descriptor, plan a load inside a fixed staging budget, and say why a model name has exactly one reading. The later chapters add the rest: to place models and caches under a budget, to schedule many requests onto one device, to make generation faster without changing its output, to expose an engine safely and to run it so that it can be seen and stopped.
