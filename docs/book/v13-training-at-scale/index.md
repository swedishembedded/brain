# Volume XIII: Training Large Models Efficiently

The first models of this book fitted in a spreadsheet's worth of numbers and trained in the time it takes to read this sentence. Nothing about them needed engineering: the data was a list, the weights fitted beside it in memory, and one process did all the arithmetic. A model of billions of numbers breaks each of those conveniences in turn. The data is a stream of records from several sources, some of them repeated, some of them overlapping the held-out set, and the way it is cut into rows decides what the loss measures. The weights, the gradients and the optimizer's moments together take several times the memory of the model, and the arithmetic they need is spread over more than one number format. The device that has the data does not have room for the model, and the one that has room does not have the time. And a run that takes a week must survive the day a machine fails, and still produce the model it would have produced.

This volume is about those breaks, taken in the order a training run meets them. It starts with the data, because nothing downstream can repair a pipeline that scores the wrong thing: how a record becomes token ids and a mask, how records become rows and batches without wasting the arithmetic or letting a position read the answer, how groups are mixed in stated shares, how duplicates and held-out overlap are found, and how the order of feeding is made reproducible. It turns to the numbers themselves, to what can be held in 16 or 8 bits and what must stay in 32, and to the loss scaling and rounding that keep a narrow format from erasing the small updates a run is made of. It accounts for the memory of a step line by line, and takes it back in three ways: by recomputing instead of saving, by storing the optimizer's state in fewer bits, and by streaming what does not fit. It then asks how little of a model has to be trained to adapt it, with low-rank adapters on a frozen and quantized base, and how adapters are merged and served. It spreads one run over many devices by data, tensor and pipeline parallelism, and says what collective communication costs in bytes. It lets a small model learn from a large one. And it closes with the checkpoint, the transaction that makes a crash a pause, and the determinism that makes the resumed run the same run.

The volume leans most on the ones before it that built and trained a model. Volume III supplied the optimizers, the schedules and the gradient check, and Volume IV the number formats, the roofline and the memory hierarchy that the later chapters count against. Volume V supplied the transformer and the training pipeline whose packed rows and loss mask this volume revisits, and Volume VI the architectures whose experts and long contexts the parallelism chapter must cut. Volume XII supplied fine-tuning on demonstrations and the replay of old data, which are the workloads this volume makes cheap. Volume XIV is the neighbour on the other side: serving takes the artifact that a run leaves behind, and asks how to get it from disk to a device and keep many conversations on it.

The order follows the dependencies. The data chapter comes first because every other chapter takes a batch as given. Mixed precision and the accounting of memory come before parameter-efficient methods and parallelism, since each is an answer to a line of that accounting: the adapters shrink the optimizer's state and the gradients, and the parallel methods divide what is left. Distillation uses the fine-tuning of the data chapter with targets that are distributions in place of tokens. The checkpoint chapter comes last among the methods because it needs to say what a run's state is, and the earlier chapters have each added to it: master weights, scale factors, shards, an order of feeding. The volume ends with a project that moves one training run from one device to several without changing what it learns, which is the check that all of the above is correct.

You can write the records of a fine-tuning set as ids, a mask and start offsets, say what each position of a row may read, and count the padding a layout computes before the run starts. You can sort records by length and state what that costs the batch, realise a mixture by listing groups and say how often it repeats a record, find exact and near duplicates with hashes and MinHash and keep the held-out set clean, and give a run an order that a restart and a team of workers can recompute. The later chapters add the rest: to decide where each number of a step lives and in which format, to cut the memory of a step to what the device holds, to adapt a model by training a few million numbers, to divide a run over devices and compute what the division costs, and to make a crashed run produce the model it would have produced.
