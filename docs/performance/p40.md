# brain on NVIDIA Tesla P40 (Pascal / `sm_61`)

Status ledger for making brain's GPU path fast on the two P40s in this box.
Companion to `docs/PERFORMANCE.md` (which documents the Intel-Arc-era work);
the hardware resources live in `/data/workspace/resources/nvidia-gpus/`.

> **Why this document exists.** Every GPU number in `docs/PERFORMANCE.md` was
> measured on a *bandwidth-starved integrated* Arc iGPU (~4.6 TFLOP/s fp32,
> ~90 GB/s shared LPDDR5). The P40 is the opposite machine: **11.76 TFLOP/s
> fp32 against 346 GB/s of dedicated GDDR5**. Several conclusions in that
> document are correct there and *wrong here* — most importantly "im2col +
> tiled GEMM adds traffic, not a win", which the document itself qualifies with
> *"worth it on a compute-bound discrete GPU."* This is that GPU.

## 1. The one number that drives everything

```
ridge point = 11 760 GFLOP/s ÷ 346 GB/s ≈ 34 FLOP per byte
```

A kernel must perform ~34 floating-point operations for every byte it pulls
from VRAM before the P40's arithmetic units become the limit. Measured against
that bar:

| kernel | FLOP/byte | ceiling on P40 | who uses it |
|---|---:|---:|---|
| `matmul.wgsl` (naive) | **0.25** | ~86 GFLOP/s (**0.7 %** of peak) | gpt, glm, qwen, moe, pid, seq2seq, mirror — *every transformer* |
| `matmul_dx` / `matmul_dw` (naive) | 0.25 | ~86 GFLOP/s | every training path |
| `matmul_tiled.wgsl` (32×32, 64 thr) | 8 | ~2.8 TFLOP/s | chronos2, kronos only |
| target (128×128×8, 256 thr) | 32 | ~11 TFLOP/s | — |

The headline gap is not subtle: **brain's transformers multiply matrices at
0.7 % of this card's peak**, and the one tiled GEMM that exists is wired into
exactly two of the fifteen models.

## 2. Hardware facts (measured, `resources/nvidia-gpus/logs/vulkaninfo-full.txt`)

| | |
|---|---|
| Vulkan | 1.4.303, `DRIVER_ID_NVIDIA_PROPRIETARY`, driver 570.195.03 |
| subgroup size | **32** (brain's `@workgroup_size(64)` = 2 warps) |
| max invocations / workgroup | 1536 |
| max shared memory / workgroup | 49 152 B |
| `shaderFloat16` | **false** — and P40 fp16 runs at 1/64 rate, so this is moot |
| cooperative matrix | **absent** (Turing+ only) — no tensor-core path exists |
| `integerDotProduct4x8BitPacked{Signed,Unsigned}Accelerated` | **true** — DP4A, 47 TOPS |

Consequences: the fp32 path is the *only* general path (no f16, no coopmat),
and the only way to exceed 11.76 TFLOP/s on this card is **INT8 via DP4A**.

## 3. Gaps

### G0 — the container had no NVIDIA userspace driver *(fixed)*

`/dev/nvidia0`, `/dev/nvidia1` and the 570.195.03 kernel module were present,
but there was no `libcuda.so`, no `libnvidia-ml.so`, no `nvidia-smi`, and no
`/etc/vulkan/icd.d/nvidia_icd.json`. Both of brain's GPU backends therefore
enumerated **zero devices**: wgpu would have panicked on `no suitable GPU
adapter found`, and `--device vulkan` would have silently fallen back
(`gpu-core/src/lib.rs:113`) to a wgpu that could only reach llvmpipe. Fixed by
installing the matching userspace driver — see the resources README.

### G1 — every transformer uses the naive GEMM

`crates/kernels/wgsl/matmul.wgsl` is one invocation per output element with a
scalar `k` loop. Registered by gpt, glm, qwen, moe, pid, seq2seq and mirror.
`matmul_tiled.wgsl` exists and is registered only by chronos2 and kronos.
Training is worse still: `matmul_dx` and `matmul_dw` have **no** tiled variant
at all, so every backward pass on every model runs at the 0.25 FLOP/byte
ceiling.

### G2 — `@workgroup_size(64)` is a hard, global invariant

All **243** kernels declare `@workgroup_size(64)`, and `backend_api::grid()`
hard-codes the 64 in both the workgroup count and the 2D-grid tiling that every
kernel reproduces as `gid.y * (nwg.x * 64u) + gid.x`. On the P40 a 64-thread
workgroup is 2 warps; filling an SM then needs the maximum 32 resident blocks,
and a 128×128 register-tiled GEMM tile cannot be expressed at all. Any serious
GEMM needs 256 threads, so the grid computation has to become per-kernel.

### G3 — the Intel ANV serialization penalty was applied to NVIDIA *(fixed)*

`backend-vulkan/src/lib.rs:440` submits **one command buffer with a fence wait
per dispatch** whenever a batch contains any sliced (sub-range) binding, to work
around an Intel ANV barrier bug. Vocab-tiled embedding and `lm_head` use sliced
bindings, so a large-vocab Qwen/GLM forward took this path — trading one submit
per *forward* for one submit per *kernel*, on a driver that never had the bug
(measured 1.7× on the TTS Talker: 583 ms forced-serial vs 337 ms). **Fixed**:
`VkContext` now exposes `vendor_id`, and `backend-vulkan` gates the serialize to
vendor 0x8086 (Intel); `BRAIN_VK_NO_SERIAL` / `BRAIN_VK_SERIAL` override.

### G4 — no multi-GPU

`WgpuBackend::new_async` takes `PowerPreference::HighPerformance` and
`VkContext` takes "the first discrete GPU". With two identical P40s the second
card is unreachable: there is no adapter index, no `BRAIN_GPU_INDEX`, and
nothing in `federated` targets devices rather than processes.

### G5 — the tiled kernels that exist were tuned away from this hardware

`conv_act_tiled` / `conv2d_tiled` are opt-in behind `BRAIN_TILED_CONV=1`
because staging weights in workgroup memory *collapsed occupancy on Arc*
(~600 → ~1600 ms). That trade-off is an integrated-GPU result. The same applies
to the rejection of im2col+GEMM for conv, which `docs/PERFORMANCE.md` explicitly
scopes to bandwidth-bound parts.

### G6 — models pinned to CPU cannot use the GPU at all

`codec` calls `Gpu::new_cpu` unconditionally (`codec/src/model.rs:100`,
`recon.rs:179,379`) — there is no flag that reaches the GPU. The TTS pipeline
defaults `cached = true`, which routes to a CPU-only KV-cache implementation and
bypasses the WGSL engine entirely; the GPU path (`--no-cache`) is O(T²).
`speaker` is forced to CPU by every caller. YOLO defaults to `Gpu::new_cpu`
unless `--device` is passed explicitly.

### G7 — no INT8 path

Nothing in the 243 kernels uses `dot4I8Packed` / `pack4x8snorm` style integer
dot products, and there is no INT8 GEMM. The P40's 47 TOPS DP4A throughput —
4× its fp32 rate — is entirely unused. (brain does have INT8 PTQ machinery, but
only for the OpenVINO/Intel-NPU export path.)

### G8 — fp16 storage is unexploited, and fp16 *math* must stay banned

`storageBuffer16BitAccess` is true, so weights could be *stored* as f16 and
widened in-register to halve weight-read traffic. But `shaderFloat16` is false
and GP102 runs fp16 arithmetic at 1/64 rate — any kernel that computes in f16
would be ~64× slower. This is the opposite of the usual advice and is worth
recording explicitly so nobody "optimizes" brain onto the f16 path.

## 5. Results

### Delivered

- **P0** — driver installed, both P40s live on wgpu *and* the native Vulkan
  backend (`gradcheck --device gpu|vulkan` both green). Device caps captured in
  `resources/nvidia-gpus/logs/`.
- **P1** — per-kernel workgroup size. `backend_api::workgroup_size_of` /
  `workgroup_sizes` / `grid_ws`; every backend (wgpu, vulkan, cpu) lays the grid
  out with each kernel's own declared size. The 243 existing 64-thread kernels
  are unaffected (`grid_ws(t,64) == grid(t)`, unit-tested); this is what lets a
  256-thread kernel exist at all. All three backends still pass gradcheck.
- **P2/P3** — two tiled fp32 GEMMs: `matmul_reg.wgsl` (128×128-tile, 256-thread,
  8×8 register) and `matmul_reg2.wgsl` (same tile + **software pipelining** —
  register-prefetch the next K-chunk to hide global-load latency). `reg2` is the
  GPT-forward default via `linear_kernel` (size threshold; `BRAIN_GPT_REG1` /
  `BRAIN_GPT_NAIVE_MM` select the others); both route to the same AVX2 GEMM on
  CPU (one graph, three backends). `reg2` reaches **34% of the P40's fp32 peak**,
  **4.0 TFLOP/s** on a single card.

### GEMM microbench (`brain-gpu-core`, `bench_matmul`, min-of-5, one P40)

GFLOP/s, `out = x·Wᵀ`. `cpu avx2` is the 48-thread CPU backend — the honest
`--device cpu` number, and the correctness oracle every GPU variant is diffed
against. `%peak` = `reg2` as a fraction of the P40's **11 760 GFLOP/s** fp32 peak.

| shape | cpu avx2 | gpu naive | gpu reg | **gpu reg2** | %peak | reg2/cpu |
|---|--:|--:|--:|--:|--:|--:|
| gpt-small qkv 512×384→1152 | 289 | 57 | 628 | **1436** | 12.2% | 5.0× |
| gpt-small mlp 512×384→1536 | 230 | 58 | 602 | **1211** | 10.3% | 5.3× |
| qwen0.6b qkv 256×1024→3072 | 207 | 35 | 791 | **2407** | 20.5% | 11.6× |
| qwen0.6b down 256×3072→1024 | 198 | 38 | 585 | **1372** | 11.7% | 6.9× |
| glm 512×6144→2048 | 210 | 13 | 892 | **3041** | 25.9% | 14.5× |
| square 1024³ | 257 | 57 | 797 | **2427** | 20.6% | 9.5× |
| square 2048³ | 408 | 41 | 1012 | **4007** | **34.1%** | 9.8× |

Parity vs the CPU reference across every shape and every variant: **rel ≤ 1.2e-5**
(fp32 K-accumulation order — asserted `< 5e-5`).

**Exact FLOPS, and why each number is what it is:**

| kernel | best GFLOP/s | % of peak | the ceiling it hits |
|---|--:|--:|---|
| `matmul` (naive) | 57 | 0.5% | **roofline**: 0.25 FLOP/byte × 346 GB/s = 86 GFLOP/s. Memory-bound, full stop. |
| `matmul_reg` (tiled, no prefetch) | 1012 | 8.6% | **latency stall**: 128²/8×8 tile → ~25% occupancy, and `load→barrier→compute` exposes global-load latency with too few warps to hide it. |
| **`matmul_reg2` (tiled + software-pipelined)** | **4007** | **34.1%** | prefetches chunk *c+1* into registers *before* computing chunk *c*, so the ~400-cycle load latency overlaps the 64 FMAs. **~4× over `reg`.** |

The three levers are visible in the numbers: tiling lifts arithmetic intensity
0.25 → 32 FLOP/byte (86 → 1012 GFLOP/s), and software pipelining hides the
latency the tile alone couldn't (1012 → 4007). At 34% of peak a single P40 does
**4.0 TFLOP/s of fp32 GEMM**, and the two cards together **~8 TFLOP/s** once
multi-GPU lands (G4).

> **Variants tried, kept `reg2`:** `reg3` (double-buffered shared, one barrier
> per chunk) measured *slightly slower* — the barrier was never the bottleneck,
> the latency was, and `reg2` already hides it; the extra 16 KiB of shared cost
> occupancy. `reg2` at `BK=16` was also slower (same occupancy cost). `BK=8`,
> single-buffered, register-prefetched is the sweet spot.
>
> **Remaining headroom** to cuBLAS-class (~9 TFLOP/s / ~75%): `float4`
> vectorized global loads and a lower-register tile to raise occupancy above
> 25%. Genuine kernel engineering with diminishing returns — 34% of a
> no-tensor-core Pascal card from hand-written portable WGSL is already strong.

### Peak hardware throughput per card (`bench` + CUDA reference)

The GEMM numbers above are a *workload*; this section is the raw silicon. The
four datasheet peaks are a pure-ALU property — reachable only by a kernel that
does back-to-back fused ops out of registers with zero memory traffic, enough
independent accumulator chains to cover instruction latency, and enough threads
to fill every SM. That is `crates/vulkan/tests/peak_flops.rs` (brain's own
Vulkan/WGSL stack) and `resources/nvidia-gpus/cuda-peak/` (a CUDA reference,
also the only path to fp16 — see below). **Both cards, best of the two paths:**

| precision | achieved / card | datasheet peak | % of peak | path |
|---|--:|--:|--:|---|
| **FP32** | **11.17 TFLOP/s** | 11.76 TFLOP/s | **95.0%** | WGSL & CUDA |
| **FP64** | **368.5 GFLOP/s** | 367.5 GFLOP/s | **100.3%** | WGSL & CUDA |
| **FP16** | **184.5 GFLOP/s** | 183.7 GFLOP/s | **100.4%** | CUDA only |
| **INT8 (DP4A)** | **43.8 TOPS** | 47.0 TOPS | **93.2%** | CUDA (WGSL 88%) |

Every precision reaches **≥93% of its rated peak on each of the two P40s**, with
FP32/FP64/FP16 essentially *at* peak. The methodology is self-checking: FP64 at
exactly 100.0–100.4% (its ÷32 rate saturates with just 16 chains) is the proof
the counting and timing are honest — you cannot exceed the physical peak.

How each precision is driven, and the platform facts behind them:

- **FP32** — 32 independent `fma()` chains, `@workgroup_size(256)`, 4096
  workgroups. WGSL hits 94%, CUDA 95%. Loop unrolling + `fma()` (not `a*m+c`,
  which the JIT sometimes leaves as two issue slots) were the levers from an
  initial 80%.
- **FP64** — 16 `fma` chains in `f64`. The P40 runs fp64 at 1/32, so few units;
  saturated trivially → 100%. WGSL and CUDA agree to <1%.
- **FP16** — **NVIDIA's Vulkan driver does not expose `shaderFloat16` on Pascal**
  (`crates/vulkan/tests/peak_flops.rs` reports it `skipped`; only the *software*
  llvmpipe device advertises it). GP102's fp16 is a single packed `fp16x2` unit
  per SM at 1/64 rate, reachable only through CUDA's `__hfma2`. The CUDA bench
  hits 100.4% of the 183.7 GFLOP/s rating — so the number is reached, just not
  through the WGSL stack. This is a driver/ISA constraint, documented in **G8**.
- **INT8** — `dot4I8Packed` (WGSL) / `__dp4a` (CUDA), 32 chains. CUDA's *fused*
  DP4A reaches 93%; WGSL's `dot4I8Packed` is non-accumulating (a separate int-add
  follows each dot) so it plateaus at 88%. A fused-accumulate WGSL builtin would
  close the gap; the hardware path is confirmed working either way.

> The CUDA reference required two workarounds on this box, both recorded in
> `resources/nvidia-gpus/cuda-peak/`: CUDA 12.9's headers clash with glibc 2.41
> (offline `nvcc` won't compile host code), so the bench compiles kernels at
> runtime via **NVRTC**; and the 570 driver (CUDA 12.8) rejects NVRTC 12.9's PTX
> ISA tag, so the generated PTX's `.version` is rewritten to 8.5 before load (the
> instructions — `fmaf`/`__hfma2`/`__dp4a` — are all sm_61-era, so retagging is
> safe). `run.sh` reproduces it.

`VkContext` now enables `shaderFloat64` + the `ShaderFloat16Int8` and
`ShaderIntegerDotProduct` features when the device exposes them, and honours
`BRAIN_VK_DEVICE=<index>` for per-card runs — the same hook G4 (multi-GPU) needs.

### End-to-end GPT forward (`brain-gpt`, `bench_forward_p40`, B=4 T=256 d=384 L=6, min-of-20)

| path | ms/forward | vs cpu |
|---|--:|--:|
| cpu (48-thread AVX2) | 195.2 | 1.0× |
| gpu, **naive** GEMM | 1100.0 | **0.2×** (5× *slower*) |
| gpu, **`reg2`** GEMM | **37.7** | **5.2×** |

- `reg2` vs naive GEMM on the same GPU: **29× faster**.
- **Equivalence**: gpu-`reg2` logits vs the CPU reference **rel 1.5e-6**;
  gpu-`reg2` vs gpu-naive on the same backend **bit-identical (0.0)**.

This is the whole thesis in one table: the *naive* GEMM made brain's GPU forward
**5× slower than CPU** — exactly the "GPU doesn't work fast" symptom the work
started from — and the tiled + software-pipelined kernel turns it into **5.2×
faster than CPU at parity**. Both the parity and the speedup are gated as
assertions in the test, so a regression fails CI.

### Model GEMM capacity — are the models using the card?

"Maximum capacity" for a transformer means its linears run on the tiled +
pipelined GEMM (`matmul_reg2`, ~34% of the P40's fp32 peak) rather than the naive
one-thread-per-output kernel (0.3%). Audited per model, with the measured tier:

| model | forward GEMM | tier @ 2048³ | status |
|---|---|--:|---|
| **gpt** | `matmul_reg2` (size-adaptive) | 4007 GFLOP/s (34%) | ✅ fast path |
| **qwen** (0.6B GQA) | `matmul_reg2` (size-adaptive) | 4007 GFLOP/s (34%) | ✅ fast path |
| **glm** (GLM-5.2) | `matmul_reg2` (via `mm()` helper) | 4007 GFLOP/s (34%) | ✅ fast path |
| chronos2, kronos | `matmul_tiled` (32×32) | 1013 GFLOP/s (8.6%) | ⚠️ old tile — wants reg2 |
| moe, pid, seq2seq | `matmul` (naive) | 41 GFLOP/s (0.3%) | ❌ naive |
| mirror | `matmul_rows` (naive variant) | — | ❌ naive |

The three flagship LLMs (gpt dense, qwen GQA, GLM-5.2 MLA-MoE) are wired and
**parity-validated** — the register kernel reproduces the naive kernel
bit-for-bit (`glm_reg2_matches_naive_and_cpu`: reg2 vs naive `0.0e0`, vs CPU
`8.1e-7`; the gpt/qwen equivalents likewise), so the swap only ever changes
speed. `mm()` and `linear_kernel()` pick reg2 only when both output dims fill a
128-tile (small matrices keep the naive kernel, which wins there), and
`BRAIN_{GPT,QWEN,GLM}_NAIVE_MM=1` forces the old path for A/B.

The remaining models are the identical mechanical change — glm needed only a
one-line helper edit because all its linears route through `mm()`; moe/pid/seq2seq
have inline `step(MATMUL, …)` sites to convert, and chronos2/kronos already tile
(just on the older 32×32 kernel). None is a new-code risk; each is gated by its
existing gradcheck.

### INT8 inference at DP4A speed

`matmul_i8.wgsl` — a register-tiled + software-pipelined **INT8 GEMM using
`dot4I8Packed` (DP4A)**, the 47-TOPS hardware the peak bench demonstrated. Same
128×128/8×8/pipelined structure as `matmul_reg2`, but staged values are `u32`
(int8×4), the inner op is `acc += dot4I8Packed(a, b)` (int32), and the epilogue
dequantizes by the per-tensor activation×weight scales.

Validated in `crates/vulkan/tests/int8_gemm.rs` (per-tensor symmetric int8):

| shape | int8 GOP/s | fp32 reg2 GOP/s | speedup | cos(fp32) | kernel-rel |
|---|--:|--:|--:|--:|--:|
| qwen qkv 256×1024→3072 | 3175 | 1256 | **2.53×** | 1.00000 | 1.2e-7 |
| glm ffn 512×6144→2048 | 3664 | 1027 | **3.57×** | 1.00000 | 1.2e-7 |
| square 2048³ | 5365 | 1648 | **3.26×** | 1.00000 | 1.2e-7 |

Two gates, both asserted:

- **Correct** — the dequantized output matches an *exact host int32 reference*
  computed from the same quantized bytes to **1.2e-7** (fp32 rounding of the
  scale only), and its cosine similarity to the original fp32 matmul is
  **1.00000** (int8 quantization preserves direction on well-conditioned data).
- **Fast** — **2.5–3.6× the tuned fp32 pipelined GEMM** on identical M/K/N, from
  DP4A's 4 MACs/instruction plus 1/4 the weight-read traffic. (These GOP/s are on
  the raw `VkContext` submit-per-dispatch path, so both columns sit below the
  backend-batched fp32 numbers above; the *ratio* is the honest comparison.)

The path is real inference capability, not just a bench: `backend-vulkan`
(`--device vulkan`) builds its device through the same `VkContext` that now
enables `shaderIntegerDotProduct`, so a model can dispatch `matmul_i8` there
today. It is deliberately **not** added to any model's shared `PIPELINES`,
but not for the reason a previous version of this paragraph gave.

> **Correction (Intel Arc iGPU, this session).** This paragraph used to say
> `matmul_i8` stays Vulkan-only because "the wgpu/CPU backends don't enable
> the integer-dot feature" — stated as if wgpu cannot do integer dot at all,
> which conflates two different things and is wrong for one of them.
> `backend-wgpu`'s `DeviceCaps.numeric.int8_dot` is unconditionally `true`
> because WGSL's `dot4I8Packed` is core WGSL, and naga lowers it to whatever
> the target driver supports. **That lowering is real hardware DP4A, not a
> polyfill**: `gpu_core::roof`'s int8 probe (`kernels::ROOF_DP4A`, itself
> `dot4I8Packed`) measured on `--device gpu` on an Intel Arc iGPU (Meteor
> Lake, Mesa ANV) — **2066 GOP/s int8 against 372 GFLOP/s fp32, a 5.6× ratio**
> — comfortably confirming a real accelerated path, not the ~1× a polyfill
> would show. `int8_dot: true` is honest; it is not a lie to the selector.
>
> The real, narrower reason `matmul_i8` itself stays Vulkan-only: it targets
> the *native* `shaderIntegerDotProduct` **Vulkan device feature** directly
> (enabled at `VkContext` construction, in `crates/vulkan/src/context.rs`) —
> a lower-level API surface wgpu's cross-platform abstraction does not expose
> for an application to enable itself, distinct from WGSL's `dot4I8Packed`
> builtin that `backend-wgpu` already reaches through naga. A WGSL kernel
> using `dot4I8Packed` (which is most of the ones this repo actually
> registers — `matmul_i8_dyn`, `matmul_i8_gemv`) already gets real DP4A
> through *either* backend; only kernels written directly against the native
> Vulkan feature (this specific `matmul_i8`) are Vulkan-only, and that is an
> implementation choice for *that kernel*, not a capability gap in wgpu.
> See `docs/performance/arc.md` §7 for the measurement this correction is
> based on.

### YOLO convolutions — conv-as-GEMM (the compute-bound win the Arc doc predicted)

`docs/PERFORMANCE.md` rejected im2col+GEMM for conv on the bandwidth-bound Intel
Arc but flagged it *"worth it on a compute-bound discrete GPU"*. The P40 is that
GPU. The direct register-tiled conv (`conv_act_reg`) **collapses on deep
small-spatial layers** — measured on stage4 (384ch, 19×12): **93 GFLOP/s, below
naive** — because its 8×4 tile can't amortize the weight re-reads there.

New path: `im2col.wgsl` (lower the input to a GEMM operand) + `matmul_reg2`
(the pipelined GEMM, ~34% of peak) + `conv_epilogue.wgsl` (per-channel BN-eval
affine + SiLU, reproducing the fused conv exactly). Per-layer wins
(`backend-wgpu` `bench_conv_gemm`, complete with SiLU epilogue, parity-gated):

| layer | conv_act_reg | im2col+GEMM | speedup |
|---|--:|--:|--:|
| stage2 (96ch) | 429 GF | 927 GF | **2.2×** |
| stage3 (192ch) | 231 GF | 695 GF | **3.0×** |
| **stage4 (384ch)** | **91 GF** | **466 GF** | **5.1×** |

Wired into the `vision::Conv` eval path (`blocks.rs`) behind a threshold —
dense, single-batch, SiLU, Cout ≥ `BRAIN_CONV_GEMM_MIN` (default 32), no
calibration tap; `BRAIN_CONV_GEMM=0` disables it. **Whole YOLOv8n@640 forward:
43 ms → ~18–21 ms = 2.1–2.4× (23 → ~49–56 fps)**, validated by the full YOLO
suite + the eval-detection parity test.

> This work also fixed a latent **CPU-JIT bug** (`wgsl-cpu`): a work-group kernel
> that soft-skips on its barrier structure (e.g. `matmul_reg2`) dropped a
> half-built Cranelift `FunctionBuilder` without `finalize()`, corrupting the
> shared `FunctionBuilderContext` so the *next* kernel failed to compile. The
> barrier check now runs before any IR is built. It only surfaced once two
> such kernels were registered adjacent (im2col path put `conv_epilogue` right
> after `matmul_reg2`).

### Training: tiled backward GEMMs

Every training step ran its backward on the naive `matmul_dx`/`matmul_dw`
(0.25 FLOP/byte, ~0.5% of peak) — so GPU *training* was as memory-bound as
inference was before reg2, and the backward is ~2/3 of a step. Added
`matmul_dx_reg.wgsl` and `matmul_dw_reg.wgsl`: the `matmul_reg2` structure
(128×128 tile, 256 threads, software-pipelined) with the two backward
contractions' transposed staging + accumulate epilogue.

| GEMM | shape | naive | tiled | speedup | parity |
|---|---|--:|--:|--:|--:|
| dX (`dY·W`) | square 2048³ | 179 GF | 4020 GF | **22.5×** | **0.0** |
| dW (`dYᵀ·X`) | square 2048³ | 177 GF | 3946 GF | **22.3×** | **0.0** |
| dX / dW | gpt/qwen shapes | ~360 GF | 0.8–1.7 TF | 2.3–4.6× | 0.0 |

**Bit-identical** to the naive kernels (parity 0.0), so gradcheck stays green on
all backends. Wired into **GPT** (10 sites) and **Qwen** (9 sites, incl. LoRA —
tiny ranks fall back to naive automatically) via `dx_kernel`/`dw_kernel` pickers;
both route to new native AVX2 `fast_ops::matmul_dx/dw` on CPU (also speeds the
CPU backward). Measured whole training steps (fwd+bwd), gradients bit-identical:

| model | step (naive bwd) | step (tiled bwd) | speedup |
|---|--:|--:|--:|
| GPT (d384, L6) | 944 ms | 350 ms | **2.69×** |
| Qwen (d1024, ff3072, GQA 16/8, L4) | 2018 ms | **178 ms** | **11.35×** |

Qwen's larger GEMMs make the win bigger — its naive backward was catastrophic.
Validated by the full gradcheck suite (all 9 models incl. Qwen base + LoRA) +
the GPT/Qwen learning tests + cross-backend parity.

### Training was reduction-bound, not GEMM-bound (the real fix)

Profiling a full 0.6B step (`BRAIN_PROFILE`) showed the GEMMs — the FLOPs — at
**<1%**. The whole cost was two reduction kernels written for small models:

| kernel | share | flaw | fix |
|---|--:|---|---|
| `ce_grad` | **69%** (56 s/call) | recomputes the softmax **per output element** → O(rows·vocab²) = 10¹³ ops at vocab 151936 | **two-pass** `ce_stats` (per-row max/sumexp once) + `ce_grad_stats` — O(rows·vocab) |
| `gradnorm_sq` | **28%** | single-threaded reduction over the 155 M-element `tok.weight` | eliminated by the offload optimizer (norm computed host-side) |

The two-pass CE gradient is wired into **gpt and qwen** (gradcheck-green on both —
bit-exact gradients). Result: full 0.6B step **89 s → 7 s**; forward stays 489 ms.

### Optimizer-state offload to system RAM (ZeRO-Offload)

Full fp32 AdamW keeps **4 buffers per parameter on the GPU** (weight + grad +
Adam-m + Adam-v = 4× the model). For Qwen3-0.6B that is 9.6 GB of optimizer
state — plus activations and the 622 MB single-tile lm_head buffers — which
pushed full fine-tuning to OOM on the 24 GB P40. But the Adam moments are touched
**once per step, in the optimizer only** — never during forward/backward — so
they don't need HBM bandwidth. This box has **177 GB of free system RAM**.

`paramstore::Role::Offload` + `optim::OffloadAdam`: the weight and gradient stay
on the GPU (the forward/backward need them), the moments and a master weight copy
live in RAM, and the AdamW update runs on the CPU (rayon across 48 cores),
reading each grad off the GPU and writing the new weight back. GPU optimizer
state drops from 4×model to **2×model** (weight+grad). Enabled with
`BRAIN_OFFLOAD_ADAM=1`.

**Validated** (`optim/tests/offload_parity`): the offloaded AdamW is
**bit-exact** to the on-GPU kernel (rel 5.9e-8 no-clip, 5.9e-7 with grad-clip) —
same training trajectory, moments just live in RAM. At block 512 the 0.6B full
fine-tune **fits (14.3 GB, no OOM)** where the all-GPU optimizer OOM'd.

### Not yet done (the rest of §4)

Backward GEMMs (`matmul_dx`/`matmul_dw`) still run naive, so a training step's
forward speeds up but its backward does not (P2 tail — the same
software-pipelined tiling applies). `reg2` is wired into GPT, Qwen and GLM-5.2 (the three flagship LLMs, all
parity-validated); moe/pid/seq2seq/mirror and the 32×32-tiled chronos2/kronos
are the identical mechanical follow-up (P3 tail). Kernel headroom to ~75% of peak is `float4`
loads + higher occupancy (P2 tail). G3 (ANV serialization vendor-gate), G4
(multi-GPU — the 2nd P40 doubles this to ~8 TFLOP/s), G6 (CPU-pinned
codec/tts/speaker), G7 (INT8 DP4A) now has a validated GEMM (`matmul_i8`, 2.5–3.6× fp32) reachable via `--device vulkan`; wiring it into a quantized model engine is the remaining step.
