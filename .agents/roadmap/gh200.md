# GH200 (Grace-Hopper) support - roadmap

Ledger for making brain fast and correct on an NVIDIA GH200 (Hopper GPU, Grace
Arm CPU, coherent NVLink-C2C) while older GPUs keep valid implementations.
`cuda.md` is the ledger for the CUDA backend itself; this file is the plan and
status for the work that targets this machine class. Same rule as there: no
hardware is hardcoded; everything below is a query result or a measurement,
dated and attributed.

## Release bar

Every declared model path executes correctly; every accelerated path reports
what actually ran; older GPUs retain valid implementations; no kernel is
removed without a demonstrated replacement; GH200 performance is established by
reproducible end-to-end measurements, not by kernel microbenchmarks alone.

## Decisions

- First milestone is whole-catalogue CUDA breadth and correctness (generated
  tier compiles and agrees with the reference for every kernel a model path
  reaches), before tuning.
- Two toolchain lanes from the start: CUDA 12.x (Pascal through Hopper) and
  CUDA 13.x (Hopper and newer). CUDA 13 dropped offline compilation for
  Maxwell/Pascal/Volta, so the 12 lane is what keeps the P40 class working.
- cuBLASLt and cuDNN lead for dense GEMM and attention; native kernels only
  where a library does not fit (quantized formats, decode GEMV, MoE, GDN,
  irregular shapes).
- Toolchains install under a user prefix (`make cuda/install LANE=12|13|nsight`,
  `scripts/build/install-cuda-userspace.py`); nothing needs root.

## The machine (queried, this node)

Hopper cc 9.0, 132 SMs, 60 MiB L2, 227 KiB opt-in shared memory per block, 120
GB-class HBM3. The driver reports `pageable_memory_access`,
`pageable_via_host_page_tables`, `concurrent_managed_access`,
`direct_managed_from_host` and `host_native_atomics` all set (ATS addressing),
so ordinary host allocations are GPU-addressable; `integrated` is 0, so brain's
existing integrated-GPU test is NOT a coherent-memory test. Thread-block
clusters, memory pools and GPUDirect RDMA are reported supported.
`tools/gh200-probe` reproduces everything below (`make gh200/probe`).

### Measured ceilings (probe, median of 10 after warmup, CUDA events)

| Quantity | CUDA 13.0 lane | Notes |
|---|---|---|
| HBM read / write / copy (GB/s) | 3810 / 3630 / 3447 | 4 GiB buffers |
| Pinned host, GPU read / write (GB/s) | 63 / 62 | through C2C |
| Pageable system memory, GPU read (GB/s) | 139 | first touch on CPU, ATS |
| memcpy H2D / D2H pinned (GB/s) | 75 / 62 | |
| Kernel launch latency (us) | 5.3 | empty kernel, back to back |
| GEMM 8192^3 fp32 / tf32 (TFLOP/s) | 45 / 410 | cuBLASLt |
| GEMM 8192^3 fp16 / bf16 (TFLOP/s) | 843 / 833 | |
| GEMM 8192^3 fp8 e4m3 / int8 (TFLOP/s) | 1622 / 1548 | |

The CUDA 12.9 lane measures within a few percent of these. Small GEMMs fall far
short of peak (1024^3 bf16 reaches about a fifth of the 8192^3 rate), which is
where decode-shaped work lives.

## Verified findings that shaped the plan (source audit, rev 6c849ced)

- `ArchDesc` had seven dtype tier slots for eleven `DType` variants; any
  NF4/FP4/FP8 capability query indexed out of bounds. Fixed: one `DType::ALL`.
- `NativeSpec::Cuda` has no dynamic shared memory, clusters, typed arguments or
  target suffix; launches pass zero dynamic shared memory.
- NVRTC discovery knew only `.so.12`, `.so.11` and the unversioned name; no
  `CUDA_PATH`. Flags compile for `sm_<cc>` (never `sm_90a`) with `--fmad=false`.
  No ahead-of-time cubins exist, so a driver-only machine cannot run the
  generated tier.
- The CUDA stream is blocking by design; there is no `cuEvent*` binding, so
  CUDA kernel times are host wall-clock and `device_timed` is false.
- The provider seam covers five `Ops` methods and `CudaProvider` accepts only
  plain F32 forward matmul. About 22 model crates choose kernels by
  `block::gemm_variant`/`pick_gemm`/`gemv_tier` or by kernel name, and qwen3
  serving hand-dispatches its GEMM and attention kernels, so a faster provider
  alone speeds up almost nothing.
- 533 WGSL kernels (plus template variants); nothing enumerates which are
  CUDA-generatable. The generator rejects barrier-in-loop, atomics, f16 and
  non-1-D workgroups; `dot4I8Packed` lowers to a scalar loop.
- Generated index arithmetic is `unsigned int`: buffers past 2^32 elements wrap.
- CUDA reports a 2 GiB binding limit on purpose (model tile budget divisor).
- Only `cuMemAlloc`, `cuMemAllocHost` and `cuMemGetInfo` are bound: no managed or
  system-memory policy; a GH200 is treated as a discrete HBM-only card.
- `Collective` payloads are host `Vec<f32>`; tensor/pipeline/expert parallelism
  have no device-resident path and expert parallelism has no code.
- aarch64: `open` was declared non-variadic (denied by current rustc),
  `c_char` was assumed signed in the Vulkan extension list, and the NEON int8
  dot existed but was never selected. All fixed; the NEON test now runs on
  Grace.

## Phases and status

- [x] **0.1** Toolchain lanes install without root; both build and run the probe.
- [x] **0.2** aarch64 build, lints and the CPU backend's tests clean.
- [x] **0.3** ArchDesc dtype-slot defect fixed with a regression test.
- [x] **0.4** Baseline machine characterization recorded (above).
- [x] **0.5** The existing CUDA tests run on the GH200 and now execute instead of
  skipping. They found a real defect (a handle blocked by another handle's graph
  capture; lesson 201) and a racy assertion, both fixed.
- [ ] **0.6** Baseline of today's brain on this node (`brain roofline`,
  `brain perf`, Qwen3 latency/throughput) and the real-model set pulled.
- [ ] **1** Capability model, operator contract v2, numerical policies, coverage
  report, selection that filters on eligibility then measured cost.
- [~] **2** Toolchain and launch interface: NVRTC/libcuda discovery (done for
  NVRTC), `sm_90a` targets (done: `nvrtc::Target`, `ArchFeatures`, cache key
  covers target/flags/specialization/ABI), AOT cubins and manifests (done:
  `make cuda/aot`, `backend_cuda::aot`, PTX fallback, driver-only tests),
  `NativeSpec::Cuda` v2 (done: `CudaLaunch` with dynamic smem and opt-in,
  cluster dimensions through `cuLaunchKernelEx`, typed by-value scalars, an
  occupancy query, all preserved by graph capture and replay, proven on the
  GH200 with a distributed-shared-memory probe; TMA tensor maps open),
  aarch64 container recipe.
- [~] **3** Whole-catalogue generated-CUDA coverage and a numerical harness over
  every kernel and every reachable model path; per-model smoke matrix.
  Done: `make cuda-coverage` (generate + NVRTC-compile every kernel for the
  device); workgroup-uniformity analysis so barriers in uniform loops and
  uniform early returns translate; local_invocation_index; scalarised vector
  types; inlined helper functions; bit-exact golden tests for vectors and
  calls. Coverage went from 473 to 510 of 533 kernels runnable, none broken;
  the refused remainder is the 3D-reconstruction and splatting family (nested
  structs) and one kernel needing `arrayLength`. Also done: `Gpu::share`,
  `BRAIN_BACKEND`, a default backend that follows the device registry, and
  `Gpu::new_gpu` for code that means "a GPU". Open: struct support, the
  `arrayLength` ABI, numerical checks of the newly translated kernels at model
  level (`make test/cuda-matrix`), template variants.
- [~] **4** Device event timing (in progress), pooled allocation, explicit dependencies,
  separated memory limits, 64-bit indexing.
- [ ] **5** cuBLASLt provider, model call sites migrated onto the shared
  operator layer, native GEMV/quantized kernels where libraries do not fit.
- [ ] **6** Attention (cuDNN first), MoE/GDN, convolution, reductions, optimizer.
- [ ] **7** GH200 memory placement (HBM / Grace LPDDR tiers, managed/system
  allocation policies) and device-resident collectives (NCCL).
- [ ] **8** Full validation, soak, legacy regression, kernel retirement.

## Real-model evaluation set

Pulled into the model store for end-to-end work: Qwen3 0.6B/1.7B/4B/8B/14B,
Qwen3.8-27B (FP8 and its GGUF), Qwen3.6-35B-A3B (FP8 and bf16), Qwen3-VL
2B/4B/8B, Qwen3-ASR-1.7B, Qwen3-TTS-0.6B, DeepSeek-R1-Distill-Qwen 1.5B/7B.
Qwen3.6-35B-A3B is the model to make run really well.

## Not verifiable on this node

Multi-GPU scaling (one GPU), MIG/MPS, and Pascal-class numerics and performance
(no such card here): those gates need other hardware and stay open until run.
