# deepseek2ocr - roadmap

Scope: DeepSeek-OCR (`crates/deepseek2ocr`, `deepseek2`, `sam1`).

DeepSeek-OCR: a document-image-in, text/markdown-out model. DeepEncoder (SAM
ViT-B windowed+global tower with decomposed relative position bias -> a 16x
conv token compressor -> CLIP-L/14 with its patch embed bypassed in favor of
the compressor output) feeds a DeepSeek-V2-family MoE decoder (12 layers, 64
routed experts top-6 + 2 unweighted shared experts, plain MHA -- NOT MLA).

Real-weight goldens: `testdata/deepseek-ocr/real/{vision,decoder}.safetensors`
+ `manifest-real.json`, regenerated by
`tools/goldens/deepseek_ocr_convert_llamacpp_dump.py --sam-dump <dir>
--decoder-dump <dir>` from llama.cpp graph-eval dumps (that script's header is
the reproduction recipe, including the `common/debug.cpp` patch needed to make
the callback write FULL rather than truncated tensor data). `testdata/` is
gitignored, so these are re-derived, never committed.

Checkpoint: `ggml-org/DeepSeek-OCR-GGUF`, Q8_0 pair, in the model store at
`ggml-org/DeepSeek-OCR-GGUF/{DeepSeek-OCR-Q8_0.gguf,mmproj-DeepSeek-OCR-Q8_0.gguf}`.
Loader: `crates/gguf` (new shared GGUF import layer, architecture-dispatched
off `general.architecture` / `clip.projector_type`), with dedicated
`deepseek_ocr` (LM) and `deepseek_ocr_vision` (mmproj) modules. Both files
import with full two-way tensor coverage (verified by test).

## Facts pinned from the real GGUF headers (not assumed)

LM (`deepseek2-ocr` architecture):
- 12 layers, embed 1280, 10 heads = 10 kv heads (head_dim 128) -- **plain MHA,
  not MLA** (no `attn_q_norm`/`attn_k_norm`/MLA-shaped tensors present;
  matches the official HF config's `use_mla: false`).
- vocab 129280, ctx 8192, RMSNorm eps ~1e-6.
- MoE: `leading_dense_block_count=1` (layer 0 dense, ff 6848), layers 1-11
  MoE with 64 routed experts (ff 896) top-6, 2 shared experts **fused into one
  1792-wide SwiGLU MLP with no shared-expert gate tensor** -- they are summed
  unweighted, so the fused width IS the sum, not two separate 896-wide MLPs to
  reassemble at import time.
- The 64 ROUTED experts stay fused at import too: `blk.N.ffn_*_exps.weight` is
  already `[64, out, in]`, every expert's matrix back to back, and brain keeps
  it as ONE parameter (`blocks.N.mlp.experts.{gate,up,down}.weight`). Inference
  binds that bank straight to `model::moe::expert_fwd_grouped`; the training
  forward/backward address one expert inside it through `expert_fwd`'s
  `w_off`.
- `expert_group_count=1`, `expert_group_used_count=1` (no group-limited
  routing).
- **No `scoring_func`/`topk_method`/`norm_topk_prob`/`routed_scaling_factor`
  keys exist in this file's KV at all.** llama.cpp's compiled-in default for
  this arch is what actually runs: plain softmax router, top-6, no
  renormalization, scale 1.0, no group masking. This is not a reading of the
  HF config defaults, it's a fact about what the GGUF's own consumer (llama.cpp)
  does with an absent key -- confirmed via the merged PR, not guessed.
- `rope.dimension_count = 0`: not a placeholder -- llama.cpp never reads
  `n_rot` for this arch's attention branch. It ropes the full `head_dim=128`
  in **NEOX** (half-split) layout and asserts `freq_base==10000` (the file
  carries no `rope.freq_base` override, so the library default applies).
- `output.weight` present separately from `token_embd.weight` -> untied
  lm_head, as expected.

Vision (`clip` architecture, `clip.projector_type=deepseekocr`, the mmproj
file, 476 tensors):
- SAM tower: 12 blocks, embed 768, 12 heads, window 14. Global (unwindowed)
  layer indices `[2,5,8,11]`, derived from the rel-pos table extents in the
  real tensor shapes (not from a KV key -- none exists for this).
- CLIP tower: 24 blocks, embed 1024, 16 heads, patch 14, image_size 224 (the
  encoder's *native* size before DeepSeek's patch-embed bypass; the real
  input token grid comes from the compressor output, not this field).
- `clip.vision.feed_forward_length = 64` is a **converter bug** in the file
  itself (`heads*4` computed instead of `width*4`) -- llama.cpp only logs this
  field, never dispatches on it, so it's inert. Real FF widths (4096 CLIP,
  3072 SAM) come from actual tensor shapes. Left as-is upstream; our config
  extraction derives from tensor shapes, not this key.
- llama.cpp's own tensor names for this tower (`v.sam.blk.N.*`,
  `v.sam.{neck,net_2,net_3,patch_embd,pos_embd}`, `v.blk.N.*`,
  `v.{class_embd,patch_embd,position_embd,pre_ln,image_newline,view_seperator}`,
  `mm.model.fc`) are the ones the mmproj loader classifies against -- these
  differ from the HF checkpoint's `sam_model.*`/`vision_model.*`/`projector.*`
  prefixes, which are irrelevant here since we are not importing safetensors.

## Questions that were open, and how each was CLOSED (Phase 4 capstone)

- **Vision-concat order: CLOSED, `[clip_spatial, compressor_flat]`.** Pinned
  twice independently: the golden dumper builds it that way and asserts the
  halves by slicing them back out (`findings.vision_concat`), and llama.cpp's
  own consumer of this GGUF does `ggml_concat(ctx0, clip_out, sam_out, 0)`
  (`tools/mtmd/models/deepseekocr.cpp`), concatenating along the row width with
  CLIP first. `crates/deepseek2ocr/tests/tiny_ref.rs` asserts each half against
  its own source tap at widths 14 and 11; mutation-verified (swapping the two
  drops `vision_concat` to cosine 0.064 and trips the explicit half assertion).
- **CLIP `pre_ln`: CLOSED, and it was a real fixture defect.** The tower applies
  ONE LayerNorm to `[cls; tokens] + pos` before block 0 (`v.pre_ln`) and has no
  post-LN -- it is not a `norm1`/`norm2` pairing question at all. The original
  golden had no `pre_norm` and therefore did not model the real checkpoint;
  the regenerated fixture carries `clip.pre_norm.{weight,bias}`.
- **Row-layout token count: CLOSED from the reference consumer**, and the
  earlier sketch in this file was WRONG in two details. llama.cpp's
  `clip_n_output_tokens` / `clip_graph_deepseekocr::build` give:
  * global (overview) view: `h*(w+1) + 1` rows -- one `image_newline` after each
    of the `h` token rows, then ONE `view_seperator` terminating the view;
  * local tiles: `(g*tiles_w + 1) * g` rows per **tile row**, with the tiles of
    one tile-row **interleaved by token row** (tile 0 row y, tile 1 row y, ...,
    then one newline) and **NO separator** anywhere in the local branch.
    "The same as the global view, per tile" was the wrong reading.
  Implemented and unit-tested in `crates/deepseek2ocr/src/rows.rs`. The one thing
  still unverified is the ORDER of the two blocks (global-then-local as built),
  because the preprocessor that orders the views is outside the graph builder;
  it is flagged in that module's header and changes no row count, so only a real
  forward can settle it.

## New facts pinned by the capstone

- The CLIP position table lives on the checkpoint's **native square** grid and
  is bicubically resampled (torch `align_corners=False`, `a = -0.75`) onto the
  compressor's output grid, class-token row lifted out and re-inserted at index
  0. At real scale both grids are 16x16, so the resample is the identity and a
  bug there is invisible; the fixture runs 3x3 -> 4x2 (height up, width down).
- The composite is **batch 1**: `sam1`'s windowed spans' storage-binding offsets
  are not 256 B aligned across a batch stride. The golden fixture was
  regenerated at `batch = 1` to match.
- The golden's `sam_embed = 10` was **not dispatchable** (`16 | d_model` is
  forced by a 12-row window at 64-float binding alignment); the fixture now uses
  16 = 2 heads x head_dim 8, and asserts the rule in-script so a future
  regeneration cannot reintroduce it.

## New facts pinned by the real-weight phase (Phase 5)

Everything here is read off the shipped checkpoints or measured against
llama.cpp running them - not inferred from a config or a reimplementation.

- **The raw (un-renormalized) router gate is now a real-weight fact, not a
  fixture claim.** In the reference's own dump, `ffn_moe_probs` sums to 1.0
  across all 64 routed experts (plain softmax) while `ffn_moe_weights` - the
  values the layer actually multiplies its expert outputs by - sums to between
  **0.222 and 0.817** across the 6 selected experts, and equals the
  corresponding `ffn_moe_probs` entries **exactly** (max_abs 0). That is
  `norm_topk_prob = false` AND `routed_scaling_factor = 1.0`, observed rather
  than argued from an absent GGUF key.
  `deepseek2::tests::real_weight_router_gates_are_raw_not_renormalized`
  asserts both halves on the reference and on brain's own gate.
- **`clip.use_gelu = true` in the shipped mmproj.** The earlier note that this
  file sets it *false* (and therefore selects quick-GELU) was WRONG, and
  `ClipVisionConfig::deepseek_ocr()` carried `QuickGelu` because of it. Fixed to
  `GeluErf`, and `crates/clip/tests/deepseek_ocr_real.rs` now asserts the preset
  against the real file so it cannot drift again. **The authority question is
  still open** and is flagged in that constructor's doc: the original CLIP-L
  uses quick-GELU, llama.cpp reads `true` as its tanh `FFN_GELU`, and brain
  follows the file's flag into exact-erf - three candidates, and no
  CLIP-internal reference tap exists to settle it (see the capture note below).
- **The CLIP tower's LayerNorm epsilon is NOT the file's key.** The mmproj
  carries `clip.vision.attention.layer_norm_epsilon = 1e-6`, but llama.cpp
  reads that into `hparams.eps` and then overwrites it with **1e-5** in its
  `PROJECTOR_TYPE_DEEPSEEKOCR` branch ("the CLIP/ViT body runs its layernorms at
  1e-5, the SAM stage uses 1e-6"); the SAM tower's 1e-6 is likewise a hardcoded
  constant in its graph builder, not a read of this key. `from_gguf` adopted the
  key verbatim and would have run CLIP at the SAM epsilon. Now overridden once,
  in `ClipVisionConfig::from_gguf`, behind the named constant
  `clip::config::DEEPSEEK_OCR_CLIP_EPS`.
- **SAM's MLP activation is exact-erf GELU, confirmed on real weights.** An
  independent longhand NumPy fp64 reimplementation of SAM block 0 (built from
  the dequantized mmproj tensors, sharing no code with brain) scores **0.99997**
  against the reference tap with erf-GELU and **0.9797** with quick-GELU. Worth
  pinning because llama.cpp derives BOTH towers' activation from the single
  `use_gelu` flag.
- **The reference is not an fp32 oracle, and the floor reflects that.** brain
  dequantizes Q8_0 to fp32 and runs fp32 GEMMs; ggml keeps the weights
  quantized and quantizes the **activations** to 8 bits per 32-element block for
  the dot product. That is a one-sided ~1e-2-relative error per matmul, so 1.0
  is not reachable and a 0.9999 floor would be wrong on the physics. The gate
  sits at 0.999 against a measured worst of 0.99944 (vision) / 0.99957
  (decoder). The same NumPy reimplementation lands at the *same* 0.9999663 that
  brain does on `sam_blk00_out` to seven digits - two independent
  implementations agreeing with each other more closely than either agrees with
  the reference is what a reference-side numeric difference looks like.
- **Tensor layouts in the reference dump, verified from the bytes.** ggml's `ne`
  is fastest-axis-first, but which axis carries what DIFFERS within the same
  graph: `sam_layer_out-N` is `(H, W, C)` with channel FASTEST (transformer-row
  form), while `sam_output` is `(C, H, W)` NCHW with channel SLOWEST (conv-graph
  form). Checked by spatial-correlation structure (0.997 adjacent vs 0.71
  opposite corners under the correct reading; 0.27 under the wrong one), not by
  reading the code.
- **The SAM -> CLIP handoff is a bit-exact identity.** Rows 1..=256 of the
  reference's assembled CLIP input are `sam_output` reinterpreted NCHW -> NLC,
  max abs difference **exactly 0.0** - so the assembly is
  `concat(class_embd, flatten_nlc(compressor_out))` with NO position embedding
  and NO `pre_ln` applied yet (those live inside the CLIP graph, after the
  concat). Row 0 is `v.class_embd` **verbatim**, which makes it a free exact
  check on the CLIP import and is asserted in two crates.
- **The `-p encode` debug input bypasses preprocessing entirely.**
  `mtmd_debug_encode_image` copies the constant `0.5f` buffer straight into a
  `clip_image_f32` and calls `clip_image_encode` - no `clip_image_preprocess`,
  no mean/std. So the network sees 0.5 everywhere, which is NOT what
  DeepSeek-OCR's real preprocessing produces for a gray image (mean=std=0.5
  would map it to 0.0). A consumer must feed the constant unnormalized.
- **No CLIP-internal or image+decoder reference taps exist, and that is
  upstream's bug, not ours.** llama.cpp's graph-eval debug callback segfaults
  deterministically right after the cls-token concat, before `build_vit`
  begins - reproducibly, with or without the full-dump patch, at multiple image
  sizes. Its production path (`llama-mtmd-cli`) runs the same graph to
  completion. So CLIP's blocks and the composed image->logits path are gated on
  finiteness and range only, with no invented cosine floor.
- **RESOLVED (fourth pass, see below): the wgpu backend used to corrupt
  `sam1` at production shape, and the parity tests used to pin the CPU
  backend because of it.** At 1024x1024 the tower's per-block buffers went
  wrong as soon as the graph held **three or more** blocks: `block_out(0)`
  moved by up to 2.1e2 purely by adding a third block, and the patch-embed
  tap stopped being spatially constant for a spatially constant image
  (deviation 6.66, *identical* for every block count from 3 to 12). The CPU
  backend was bit-identical between a 2- and a 3-block build. Ruled out at
  the time: weight values (a dense-init build reproduced it), the import
  (every parameter round-trips through the ParamStore at max abs error 0.0),
  and global attention as such (a 2-block config with one global block was
  clean). This was a device/allocation-level defect, not covered by the tiny
  gradcheck fixture. **Root-caused and fixed**: an Intel ANV Vulkan driver
  bug (missing barrier across sliced storage-buffer bindings, the same class
  `crates/backend-vulkan` already fixed for this box) was closed by
  `backend-wgpu::WgpuBackend::flush_serialized`, and the fix was confirmed
  by real evidence (not a guess) - see the "CONCLUSION" entry under the
  follow-up investigation below for the full record. **The CPU pin remains
  in `crates/catalog/src/resident_deepseekocr.rs`, but now for a scope reason,
  not a correctness one** - also detailed below.

  **Follow-up investigation (checkpoint-free reproduction, root-cause bisection,
  and a partial mitigation), still open - the CPU pin in
  `crates/catalog/src/resident_deepseekocr.rs` was NOT lifted:**

  * A minimal, seconds-not-minutes checkpoint-free reproduction exists:
    `crates/sam1/tests/wgpu_block_count_corruption.rs`. Two `SamEncoder`s share
    an identical block-0/1 prefix (same `SamViTConfig::deepseek_ocr()` geometry,
    same `init_dense` seed - its sequential draw over `param_list()` gives
    blocks 0/1 the same weights regardless of `n_layers`) and differ only in
    whether a 3rd, global-attention block exists past them. On any correct
    backend `block_out(0)`/`block_out(1)`/`patch_tokens()` must be
    bit-identical between the two builds; `backend-cpu` holds this exactly
    every run, `backend-wgpu` does not.
  * **First hypothesis, bisected out as INSUFFICIENT ALONE**: a single large
    2D-tiled dispatch. A reduced-dims variant sized only to cross
    `backend_api::MAX_GROUPS_PER_DIM`'s 65 535-workgroup tiling threshold for
    one `attn_relpos_add` dispatch was clean on both backends.
  * **What DOES change the failure rate** (three independent levers, found by
    bisecting which dispatch is necessary for the corruption at REAL
    `SamViTConfig::deepseek_ocr()` dims): disabling just the
    `attn_relpos_add` dispatch (the kernel that folds the decomposed
    relative-position bias into the score slab IN PLACE,
    `scores[idx] += rel_h[..] + rel_w[..]`, dispatched 16 times per global
    block at `attn_chunk=256` against `T=4096`, every one needing the
    65 535-workgroup 2D-tile path - `heads*qn*kn = 12 582 912` threads);
    shrinking `attn_chunk` so no `attn_relpos_add` dispatch needs 2D tiling;
    and `BRAIN_GPU_CHECKED=1` (wgpu's bounds-checked shader compilation).
  * **`attn_relpos_add.wgsl` was rewritten** to block `JB=8` keys per
    invocation (`crates/model/src/vit.rs::RelPos::add_step`/`ADD_JB` dispatches
    the matching reduced width), cutting the real shape's dispatch to
    1 572 864 threads / 24 576 workgroups - clear of the tiling threshold at
    every SAM-1 config this repo defines. Gradient-checked green on both
    backends (`crates/sam1/tests/gradcheck.rs`, unchanged pass/fail), no
    "not JIT-compiled" fallback on `backend-cpu`.
  * **This change does NOT reliably fix the checkpoint-free reproduction.**
    Measured by running `wgpu_backend_block0_is_unaffected_by_a_third_block`
    five times in a row AFTER the kernel rewrite: FAIL, ok, FAIL, FAIL, ok
    (2/5 clean). Critically, every FAILING run reported the IDENTICAL delta
    (`patch_tokens` max\|Δ\| 8.202e0, `block_out(0)` 2.816e2, `block_out(1)`
    3.894e2 - the exact same numbers as the ORIGINAL, pre-fix defect) rather
    than varying noise. A binary outcome - either every tap matches exactly,
    or every tap is off by one specific, repeatable wrong value - is the
    signature of a **missing synchronization barrier** (a read observing
    stale pre-write device memory on some schedules, the correct post-write
    value on others), not of a fixed index formula. Each of the three levers
    above measurably changing the failure rate (rather than doing nothing) is
    consistent with a scheduling/timing-sensitive race, not proof any of them
    is a red herring.
  * **A separate real-weight, full-12-layer, checkpoint-free-independent
    confirmation** lives in `crates/sam1/tests/wgpu_real_weight_parity.rs`
    (loads the real mmproj, compares `backend-cpu` vs `backend-wgpu` forward
    tap for tap - no llama.cpp golden needed) and a further checkpoint-free
    variant at 5 layers
    (`wgpu_backend_block1_is_unaffected_at_five_layers`) found `block_out(1)`
    (computed by WINDOWED attention alone, before any global block runs)
    already diverging by max\|Δ\| 1.209e2 with more total blocks queued -
    possibly the same race showing a different observable under more queued
    work, possibly a second one; not distinguished yet (one non-repeated run,
    and the first race's own measured 2/5 flake rate means a single run is
    not enough evidence either way).
  * **What is still unknown**: the actual missing barrier/ordering guarantee.
    Candidates not yet individually tested: whether `backend-wgpu`'s
    lazily-accumulated single-pass flush (`WgpuBackend::submit`/`flush_inner`,
    `crates/backend-wgpu/src/lib.rs`) correctly orders EVERY read-after-write
    it claims to across dozens of large dispatches queued in one
    `queue.submit`, versus a genuine driver-level (Mesa ANV, this box's Intel
    Arc iGPU) scheduling bug specific to many large 2D-tiled dispatches to one
    buffer. All three test files above are runnable, checkpoint-free (except
    the real-weight one, which self-skips without the mmproj checkpoint), and
    fast (`cargo test -p brain-sam1 --release --offline -- --ignored` for the
    three `#[ignore]`d ones) - re-run each SEVERAL times, not once, before
    concluding anything from a single pass or fail.

  **Root cause found by precedent, not by live reproduction (this session's
  follow-up) - a fix is applied, but the CPU pin stays until it can be
  confirmed against a live failure:**

  * `crates/backend-vulkan/src/lib.rs` already carries the answer to "is this
    brain's own flush logic or the driver": commit `b6295e36`
    ("gpu-core/vulkan: fix flaky tiled (sliced-binding) corruption on Intel
    ANV") root-caused, WITH the Khronos validation layers (both
    synchronization AND GPU-assisted validation clean, proving the kernels
    and the synchronization brain issues are spec-correct), that the Intel
    ANV Vulkan driver on this exact box's Intel Arc iGPU does not reliably
    make a prior dispatch's writes visible across a **non-zero-offset
    ("sliced") storage buffer binding** through an in-command-buffer
    compute-compute pipeline barrier, even with `ALL_COMMANDS` stage/access
    masks - but a queue submit+fence boundary IS honoured. The measured
    signature there (~15-25% intermittent, kernels/sync spec-correct) is the
    same shape as this session's own finding (every failing run reports the
    IDENTICAL wrong value, consistent with a missing barrier, not a logic
    bug). `backend-vulkan` already ships the fix: mark a dispatch `sliced`
    when any of its bindings has a non-zero offset, and in `flush`,
    serialize (submit+fence per dispatch) any batch containing a sliced
    dispatch, gated to the Intel vendor ID so every other driver keeps the
    fast single-pass path.
  * `crates/model/src/block.rs::chunked_bidir_fwd` (the generic path
    `sam1`'s global-attention blocks route through) uses `step_sliced` for
    its per-query-chunk scores matmul and context-apply, at a non-zero
    offset for every chunk past the first - so a global block's batch
    (which also contains the 16 `attn_relpos_add` dispatches implicated
    above) DOES contain sliced dispatches, on both backends. Independently
    re-reading `wgpu-core-29.0.4`'s and `wgpu-hal-29.0.4`'s (Vulkan) source
    confirmed `backend-wgpu`'s OWN barrier-request logic is textbook-correct
    for this pattern (`STORAGE_READ_WRITE` is never in the tracker's
    `ordered_uses_mask`, so a barrier is requested before every dispatch
    that touches such a buffer; `wgpu-hal`'s Vulkan backend converts that
    into a spec-correct `vkCmdPipelineBarrier`) - which is exactly the
    "spec-correct, driver defeats it anyway" shape `backend-vulkan`'s own
    validation-layer run already proved. Both backends drive the same Mesa
    ANV Vulkan implementation on this box, so the same driver bug plausibly
    explains both.
  * **Fix applied**: `backend-wgpu::WgpuBackend::flush_serialized` (new)
    mirrors `backend-vulkan`'s workaround exactly - `WgpuStep` now carries a
    `sliced` bit (set by `step_sliced` when any binding has a non-zero
    offset), `DeviceShared` carries the adapter's PCI `vendor_id`, and
    `flush_inner` serializes (one compute pass + one `queue.submit` + one
    `device.poll(Wait)` per dispatch) any batch that is on an Intel adapter
    AND contains a sliced dispatch. `BRAIN_WGPU_SERIAL=1` forces it on any
    adapter (diagnostic); `BRAIN_WGPU_NO_SERIAL=1` disables the automatic
    trigger (diagnostic). Verified: `cargo build`/`cargo test -p
    brain-sam1 --release` (7+5+2+1 non-ignored tests, all green) and `make
    test/gradcheck` (full workspace, 0 failures) both pass unchanged with the fix
    in place - it is a no-op everywhere except Intel+sliced batches, and
    introduces no regression.
  * **What this session could NOT do: confirm the fix against a live
    failure.** The checkpoint-free reproduction (`wgpu_block_count_
    corruption.rs`) that previously measured a ~40-60% failure rate did not
    reproduce even ONE failure in this session, in ANY configuration tried:
    10 sequential repeats of the original 2-vs-3-layer repro (added as
    `..._repeated_10x`), the 2-vs-5-layer "known-failing" second divergence,
    a new max-pressure 2-vs-12-layer variant (all 4 global blocks, 64 chunk
    iterations, added as `..._at_full_twelve_layers`), 4 of the max-pressure
    variant run CONCURRENTLY (independent processes contending for the same
    physical GPU), and 3 independent processes each running the 10x-repeat
    concurrently (30 more trials) - **46 consecutive clean pre-fix baseline
    trials, zero failures**, checked out from BEFORE this session's fix via
    `git stash` specifically to make sure this was the unmodified code the
    original bisection ran against. `uptime` showed the box's 15-minute load
    average at 59.58 (a 22-core machine) falling to 4.10 within the same
    session, strongly suggesting the original bisection ran under heavy
    multi-agent GPU contention this session's quieter conditions do not
    reproduce - i.e. this looks like a load/scheduling-dependent race whose
    window is currently not being hit, not a race that stopped existing.
    With no live failure to test against, before/after comparison (this
    investigation's own planned decisive experiment) was not possible - the
    fix's justification rests on the `backend-vulkan` precedent and the
    matching wgpu-core/wgpu-hal source reading, not on a reproduced-then-
    fixed failure in this session.
  * **The CPU pin in `crates/catalog/src/resident_deepseekocr.rs` is
    UNCHANGED.** Given the hard bar this investigation set for itself (10+
    consecutive clean runs BEFORE and AFTER, on a real reproduction) could
    not be met in either direction because no reproduction failed at all,
    lifting the pin now would be exactly the "looks fixed after 2 clean
    runs" mistake this file's own history warns against - regardless of how
    strong the mechanistic case is. The next session should first try to
    reproduce the original failure (deliberately loading the GPU with
    concurrent work, or running under whatever conditions the original
    bisection actually ran in) BEFORE trusting this fix enough to lift the
    pin. If a live failure IS found on unmodified code, re-run the same
    checkpoint-free tests with this fix in place (`git log --grep
    'flush_serialized'` finds the commit) for the 10+-clean-runs bar this
    file's own lessons demand.
  * **Test additions**: `wgpu_backend_block0_is_unaffected_by_a_third_
    block_repeated_10x` and `wgpu_backend_block0_is_unaffected_at_full_
    twelve_layers` in `crates/sam1/tests/wgpu_block_count_corruption.rs`,
    both `#[ignore]`d with a doc comment pointing back here - kept as
    reproductions for the next session, not strengthened into gates, since
    a clean run here proves nothing about whether the underlying race
    still exists.

  **CONCLUSION (this repo's fourth and final pass on this bug this

`paged_flash_decode_gqa_hd256` kernel documents the same defect at 128k tokens and fixes it for Qwen3.8's head_dim 256.
That kernel is now specialised at head_dim 128 with one head per kv head (`HD`/`HD4` constants, the upper half of the
workgroup owns no output channel) and `deepseek2::serve::Engine` runs it in the fast tier with the splits pinned to the
configured context (a row's attention does not depend on its batch-mates). Exactness against f64 attention at
head_dim 128, f32 and bf16 KV: worst relative error 1.3e-6 and 1.8e-6 (`model/tests/kv_tier.rs`); the real decoder's
fast tier still tracks the reference (`serve_real`: cosine 0.99995 or better, 24 of 24 greedy tokens identical).
The int8 and fp8 KV tiers read 256-channel rows and keep the triad at head_dim 128.

Same-window step times, batch 1 at a 1300-token context: 121 ms before, 10.3 ms after; batch 8: 175 ms before, 10.9 ms
after; batch 1 at 283 tokens: 63 ms before (loaded box) and 9.8 ms after.

## 2026-10-26 tiled reading (the reference's "Gundam" mode) and the global-view order

Facts read from the reference code (`modeling_deepseekocr.py`, not from llama.cpp): the image embeddings are laid out
`[local tiles, global view, view separator]` (`torch.cat([local_features, global_features, self.view_seperator])`), so
the global-first order `crate::rows` had assumed was backwards; it is local first now, with the tile mosaic's rows
(one newline per mosaic row, the tiles of a tile-row interleaved by token row) and the global view's rows each
newline-terminated, and the projector row to (view, token) map in `RowPlan::locate`. Reading policy
(`serve::Reading`): both sides at most 640 px is one aspect-fitted 640 view (111 rows, the reference's "Small" mode);
larger images are `tile_grid(640, at most 9)` tiles plus the 1024 global view; `max_tiles = 0` is the old global-only
reading. Views are prepared by `imaging::views` (Pillow bicubic and `ImageOps.pad`, byte-pinned; the old preprocess
used a non-antialiased device bicubic, which aliases a 2480 px scan down to 1024). The tile tower is a second
`DeepEncoder` at a 40x40 SAM grid whose absolute position table is resampled at load (`sam1::resample::GridSource`).

Grounding boxes are relative to the original image in every reading (a 1009x417 page is boxed over y 29-959 of 999,
not inside the padded square's band), which is what the reference's post-processing assumes; nothing is transformed.

Dense-page regression (synthetic 1654x2339 page, 15 px text, 930 reference words, `Free OCR.`, 1500 tokens, word error
rate against the rendered text): DeepSeek-OCR global view 0.884 -> tiled 0.520. A real 1960 newspaper page
(`ww1960-0601-v02n11.pdf`, page 2, rotated upright, 2x3 tiles, 908 prompt tokens) reads headlines, columns and article
text in order.

attention (scores, rel-pos bias, softmax, apply: unfused WGSL) is 1.1 s and the GEMMs 0.09 s; the 640 px tile 0.63 s;

upgrade table does not cover, where the 257-token global CLIP gets `matmul_f32_reg`. Open: fused rel-pos flash
attention for SAM, `matmul` -> native GEMM for small M, bf16 tensor cores for the linears.

## 2026-10-26 throughput lane: what an API client is told

- A model that fits no card's budget used to reach a client as the generic `the model failed to process the request` (an unclassed error
  string). The scheduler now classes that refusal `[failed-to-load]` with its own text, which names the model and the size and no path

- Capacity is re-measured already: the dispatcher's capacity probe (`nvidia-smi`, on its idle tick) raises and lowers each card's budget
  from what is free, so a neighbour that exits is noticed. What is NOT re-planned is the OCR replica set: it is decided at construction
  from the cards' free memory then, so a card that frees up later gets no replica until the server restarts (open).
- `max_tiles` is forwarded by the chat API (top level or `chat_template_kwargs`, 0 to 64); the cheap reading is `max_tiles: 0`.

## 2026-10-26 throughput lane: open, in the order the profile ranks it

1. Encoder glue, ~half of a page's GPU time and all of it memory-bound: fuse SAM's relative-position bias and row softmax into one pass

## 2026-10-27 round 2: v2's 64-client collapse, warm-up, the fused bias softmax

**The collapse is the encoder, not the scheduler.** v2 at 64 clients ran 24 to 28 pages/min (p95 130 to 160 s) against 50 at 16 clients, cold
and warm alike once the card's neighbour is accounted for (the same binary gave 23 to 47 pages/min in three fresh 64-client bursts and
56 to 60 when warm, with the neighbour at 137 to 340 W). No sequence was preempted (a counter in the preempt path read 0 over a 64-client
burst) and the K/V pool never ran dry. What is serial is the encode thread: a v2 page is ~1 s of GPU (SAM at 1024 and six 768 px tiles, then
the resampler over the tiles and the page), so the 64th page of a burst starts decoding after 64 encodes, and latency is proportional to the
page's place in the queue. The throughput lever is the cost of an encode (below) and more than one in flight; the fix made here is that the
encode thread answers each page when it is encoded (`PageEncoder::encode_many` takes a per-page callback) instead of answering a whole burst
at once, so the first pages decode while the rest encode.

**Warm-up.** `Engine::warm_up` runs a full prefill chunk (kernel compilation) and records the decode step of every row count up to the
ceiling with throwaway sequences; `PageEncoder::warm_up` encodes a small and a large page. 0.9 s and 0.5 s at load on v1; fresh servers with and without it
gave the same 64-client throughput within the neighbour's noise (cold bursts 47, 34, 23 against 30, 34, 50 pages/min), so recording is
cheap and the cold cost was not the cause. A program whose first library product is its own now freezes (the cuBLAS handle is created before
the capture opens; the warm-up hit it).

**The bias and the row softmax of SAM's global blocks in one kernel** (`attn_softmax_relpos`, 256 threads per row, one read and one write
of the score slab): SAM's device time at the global view 39.5 -> 35.5 ms, the view 50 -> 45.5 ms best of 25 (tile 21.5 ms, unchanged). The kernel
runs 0.6 ms per 200 MB chunk against a 0.12 ms floor; the 32-register row buffer is the first suspect.

## 2026-10-27 round 2: fairness of short pages against long, and the serving flags

Eight clients reading full pages and eight reading 600x400 crops at the same time (DeepSeek-OCR v1, gpu1, a neighbour at 150 to 410 W on the
card; two alternating runs per setting; crops alone: median 1.1 s, p95 1.8 s, 400 per minute):

| setting | crops median / p95 (s) | pages per min mixed (alone 52) |
|---|---|---|
| before: FIFO encoder, 1024 prefill rows between decode steps | 3.5 / 12.9 and 3.5 / 12.6 | 34.9, 35.7 |
| + cheapest-page-first encoder | 2.6 / 10.3 | 49.9 |
| + 512 prefill rows (one chunk) | 1.9 / 9.0 and 1.8 / 9.1 | 51.1, 50.1 |
| 256 rows | 2.8 / 13.5 and 1.8 / 9.3 | 37.1, 49.7 |
| 128 rows | 2.0 / 9.4 and 1.9 / 12.2 | 48.8, 40.7 |

Two causes. The encoder served its queue in arrival order, so a crop (29 ms alone, 130 ms beside a decode) waited behind full pages (0.3 to 1 s
each): it now takes the cheapest page first, discounted by the time it has waited so a page cannot be passed over forever, and drops a request
that was cancelled while it waited (`next_job`, tested). And a decode step that also admitted a page ran two prefill chunks (~80 ms) first, so
every page already decoding paid that on every step a new page arrived: 120 steps of a crop's decode at 70 ms is the crop's 8 s. One chunk
between decode steps (`PREFILL_BUDGET`) halves the crops' median and raises the pages' throughput. The tail (p95 9 s against 1.8 alone) remains.

**Serving flags.** The OCR models honour `--max-batch` (1 to 128), `--ctx`, `--kv-cache f32|bf16` and `--gemm fp32` (`ocrserve::policy`,
`OCR_POLICY`): `--gemm fp32` runs the decoder's reference tier and every vision tower on the exact fp32 kernels; the pool is sized by bytes
(bf16 128k tokens, f32 64k), so a larger batch shares it. `--weight-format` is refused by name and stops the OCR models from being served
(`brain serve --max-batch 16 --gemm fp32 --kv-cache f32` and the refusal were run).

## 2026-10-27 round 2: the dispatcher ran the OCR models eight pages at a time

At 32 clients the decode batch held 4 to 7 rows (a counter in the decode step), the encoder thread was 40% busy and every page took 24 s,
of which about 4 were decode. A trace of the group admission showed the cause: pages entered the scheduler in waves of eight (`admit job=0..7`
together, then nothing until all eight had finished, ~6.8 s a wave = 70 pages/min). The OCR residents declared no
`ResidentModel::batch_limit`, so the dispatcher gave the instance the scheduler policy's default group of eight and closed its inbox to later arrivals:
the continuous-batching scheduler underneath was never fed continuously. `OcrResident::batch_limit` now returns the engine's row count (64).

## 2026-10-27 round 2: the router's product

A decode step's profile at 64 rows and ~950 tokens of context put 13% of its device time (20.9 ms of 156 over 16 steps) in `native:matmul_f32_tiled`,
the fp32 router: a `[64, 1280] x [1280, 64]` product is ONE 128x128 tile of that kernel, one multiprocessor of 132, 0.12 ms a layer. The fast tier now
routes with the library's exact binary32 product (`LibraryGemmProvider::gemm_f32`, no TF32: the top-k stays a decision on unrounded logits), which splits the
reduction over the card; the reference tier keeps the in-house kernel it is stated against. Best step of 64 (best-of-N, engine_bench, prompt 900):

| decode step | before | after |
|---|---|---|
| 32 rows | 4.66 ms | 4.46 ms |
| 64 rows | 7.18 ms (8,900 tok/s) | 6.11 ms (10,470 tok/s) |

The rest of the 64-row step is the paged attention at 33% (3.2 ms against a 2.1 ms floor for reading 7.5 GB of bf16 K/V; fp8 K/V would halve the bytes,

## 2026-10-27 round 2: replicas follow the cards that are free

Replicas were planned once, at start, on the cards that had room then, so a card a neighbour held at start never got its replica, and a replica planned on a card
that is held later would have been refused for the budget. Now: the OCR models plan a replica on every card whose capacity holds the model
(`plan_replicas(free, capacities, ..)`), and the executor routes a job only to a replica that can run on the budgets as they are now
(`ResidencyManager::replica_can_run`, `least_loaded_replica`): one whose card is held is routed around until the capacity probe (it already raises
and lowers every card's budget from what is free) sees the card free, and a model with no replica able to run takes the first, failing with the
budget's classed reason. Tested at the manager (`a_replica_can_run_only_while_its_card_has_the_budget`), the router and the planner.
