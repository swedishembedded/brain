# cli-to-served

Scope: Moving every model-specific CLI verb into its model's served actions, turning the per-architecture CLI modules into per-model Rust samples, and reducing the `brain` binary to its generic verbs (a major release: no compatibility aliases).

## The design

- **A model capability is a served action, and only that.** Inference, training, evaluation and conversion of one model are `capability::Action`s on that model's provider, reachable from `brain serve` (HTTP, D-Bus) and from `brain <model> <action>` on the host. A param naming a file on the host is `.host_resolved()`; a trained or converted artifact also comes back as an output blob where its size allows.
- **`brain <model> <action>` is the only per-model command.** It is `crates/invoke` over the catalog: the action's manifest is its command line (every param, typed, with its default and bounds), files become input blobs, output blobs become files. No `crates/cli/src/<arch>_cli.rs` module remains and the `ARCH_HANDLERS` table is gone.
- **Per-model samples** live at `samples/models/<arch>/` (package `sample-models-<arch>`): a Rust program over that model's crate and `crates/invoke`. `<sample> <action> [flags]` runs any served action with every knob and the manifest's defaults; on top of that a sample carries what is an application rather than a capability (an interactive window, a camera viewer, a game loop, a multi-step workflow written in Rust). Flags a user must give are only those an action requires; everything else defaults in the manifest, and the action validates every value before a weight loads.
- **Shell samples** that wrapped a per-model verb either move into that model's Rust sample or call `brain <model> <action>`; a wrapper that only renamed flags is deleted.
- **Generic verbs** stay only where they are not about one model: `serve`, `caps`, `pull`, `models`, `import`, `quantize`, `finetune`, `optimize`, `prune`, `perf`, `devices`, `doctor`, `roofline`, `plan`, `gguf`. The rest go into the model or sample that owns them.

## Done

- `crates/invoke`: the action runner `brain <model> <action>` and every sample share. `invoke::main` is a per-model program's whole `main` (global `--device`/`--backend`/`--brain-data-dir`, help from the static manifest, flags checked before any weight lookup, weights from the store, a clean device drain at exit). Two checkpoints of one model that tie in the store are settled by the action's `variant` (given, else its default). The catalog is the one table of which model resolves its weights through which spec.
- qwen35: `finetune` (full, or LoRA/IA3/LoKr/DoRA on an fp32, bf16, nf4 or fp8 base streamed from a brain checkpoint or a Hugging Face directory; the tokenized folder as `data` or chat JSONL as `dataset`/`validation` blobs; `train_precision`, `activations`/`recompute`, the long-sequence settings, the held-out evaluation; a named adapter, `adapter_id` or `adapter_name`, is filed in the model store and continued unless `fresh`, an unnamed one is the `adapter` blob or lands at `save`; every step reported, cancellable between steps, seed echoed), `sample_adapter` (the streamed base with the adapter overlay on, off or both, `mode`) and `import` (a GGUF into a brain checkpoint with its MTP head, or a Hugging Face directory re-encoded once at `weight_format`) are actions of `brain/qwen35` (`qwen35::{train_actions, sample_actions, convert_actions}`); `generate` replaces `infer` and takes the LoRA `adapter` (folded into the weights once) and a GGUF as `tokenizer`. `brain qwen35 <action>` is the generic dispatch (`ARCH_TO_MODEL`), so `ARCH_HANDLERS` and its dispatch branch are gone, and `samples/models/qwen35` carries the same actions with nothing of its own.
- ltxv: `replace` is an action of `brain/ltxv` (`ltxv::replace`): SAM 2, FLUX.2 (through its served `edit`) and ArcFace come through `capability::Components`, which the catalog and samples implement over the model store (`loader::components::StoreComponents`); its work directory resumes as before. `t2v` gained `scenes`, `context_frames`, `max_window_tokens`, the reference video (`reference`, `reference_attention_mask`, their strengths) and `stage_2_ic_lora`; `v2v` a mask sequence, `strength` and `keyframes`; `extend` `seconds`; `upscale` `context_frames`; every generating action the runtime knobs (resident blocks, two-stage, VAE tiling, text-encoder precision and cache, latent dumps, the fp32 audio-video reference), host-only. A clip's frame rate from its container is honoured (it was read as an integer and dropped). `samples/models/ltxv` carries the `chain` workflow (`invoke::Workflow`); the shell videogen samples are gone.
- flux2: `text2image`/`edit` take everything the CLI verb did - inpainting (`mask`), up to eight references with the default 512 px bound (`ref_size`), the init image's size as the canvas, tiled canvases, `experimental_steps`, `ref_resolution_scale`, several adapters with their own strengths (`adapter` is a `path@strength` list, `model::adapter::AdapterSpec::parse_list`, for every model) - planned from the images' sizes alone (`flux2::request`), which is also what the scheduler keys a resident on; `lora_train` gained `ckpt_every`/`resume` (they sat on the generation actions), `precision`, `train_base`, `cache_dir`. An unset `precision` is the checkpoint's own, so a served GGUF DiT runs. `samples/models/flux2`.
- wan: `t2v` gained `dit_dtype` (it was read but not declared) and `te_device`; the global `--device` places the DiT and VAE. `lora_train`'s `report` writes the base-vs-adapted evidence (`wan::report`), its EVA-CLIP table from `report_clip` instead of an environment variable. `--variant` settles two DiTs of different sizes in one store. `samples/models/wan`.
- huginn, ouro: `catalog::resident_provider::ResidentProvider` runs a model's served actions in this process through its own residency adapter (built over the store-resolved checkpoint, one instance kept, rebuilt when the host-side engine sizing - `ctx`, `block`, huginn's `steps` - changes), so `brain <model> generate` and `brain serve` share one engine; `catalog::family_spec::FamilySpec` resolves a checkpoint by the architecture its config or card declares. `import` is an action of both, and ouro's `train` (the short in-place run, `ouro::train`) one of ouro's; the per-row unsupervised last position is now each row's. EdgeRock and Ripple keep their own providers of the same shape until they move onto it.
- qwen3tts: `synth`, `clone`, `design`, `batch`, `import`, `finetune` (the attention LoRA or the full Talker, cancellable) and `sim` are actions of `brain/qwen3tts`, which the store resolves (`qwen3tts::spec`); the residual-codebook sampling knobs are params of every speech action. The engine placement, streaming and diagnostics variables are parameters (`qwen3tts::placement`); the serving adapter streams `synth`, `clone` and `design` from its hot engine. The env-only adapters (`resident!`) move onto it model by model.

The distributed-job parameters (`job_plan`, `job_rank`, `job_secret`, `profile_collectives`) are one set in `model::job_params`, which joins the job and writes the collective profile. Every flag is a typed param (`npu::run_options` for the OpenVINO ones), a checkpoint is the role `--weights` (`--dir` for deepseekocr2) and the structural report `brain npu check` prints is `npu::check::structural_report`. They are compile- and unit-tested; running them needs OpenVINO and an NPU.
- Store-resolved weights everywhere: LLaVA (`llava::spec`), CosyVoice's S3Tokenizer and CAM++ graphs (roles of `cosyvoice::spec`, classified by graph structure), CLIP, SCRFD, ArcFace, Florence-2, FLUX.1, PuLID, Z-Image, MiniMax Music 3 and the stdio controller's Qwen3-TTS no longer read a `BRAIN_*` path; `brain_arch::Arch` has no `weights_env`/`extra_refs` and the CLI no `ensure_env_weights` gate, `RESOLVER_MIGRATED_ARCHS` or `resolver_cli`. Qwen3-VL's KV length is the `ctx` request param (`qwen3vl::caps::Capacity`, beside `max_pixels`), the scheduler's weights are `brain serve --sched-*` flags with `--max-batch` capping a run. Every retired variable is in `RETIRED_VARIABLES`.
- CLI surface: `brain perf flops`/`perf roofline` replace `flops`/`roofline`, `brain models inspect` replaces `gguf inspect`, the `fetch` alias is gone, and the top-level help describes `brain <model> <action>`, `caps` and per-action `--help` instead of every architecture. `label` and `data` stay generic (a workflow over the captioner seam, dataset tools).
- decide: `train`, `eval`, `promote`, `rollback` and `inspect` are actions of `brain/decision` (`decisions::lifecycle` declares them, `brain::decision_actions` runs them over `brain::decision_run`); `decide_cli` is gone. The catalog cannot depend on the SDK (the SDK's `text` feature depends on the catalog, a Cargo cycle), so the CLI attaches the lifecycle provider to the catalog's `DecisionProvider` (`DecisionProvider::with_lifecycle`, `caps_cli::local_provider`); the declaration sits in the catalog's manifest, so `brain caps decide`, the bounds and path gates cover it. Every file is a `.host_resolved()` param and the lifecycle is host-only: `served_manifest` keeps just `models` and `select`, so `brain serve` (with or without `--training`) never runs it. `train` is `.training()`, reports every step, stops between steps on cancellation and echoes its seed; `eval` echoes `seed` (was `--order-seed`); results are typed outputs, a `report` text blob and the `record` JSON. A failed promotion gate fails the action (exit 1) with the margins.

## Decisions for what is left

- **No environment variables.** A knob is a parameter: a generic one shared across models where the meaning is shared (`--device`, `--weights`-style roles, `seed`, `activations`), a model's or sample's own where it is not. Data flows along the call path (provider construction, invocation, workflow call), never from process-global state; each migration removes the env reads it touches, and the serving adapters' `from_env` constructors give way to the model store and explicit parameters.
- **Knobs only a host can set** (a file on the serving machine, a memory placement such as LTX's resident blocks or VAE tiling) are params declared `.host_resolved()`: `brain <model> <action>` and samples set them, a remote caller cannot.
- **A checkpoint role is a `--<role> PATH` flag**, never an action param: `invoke` takes every role the model's spec declares (LTX's `spatial_upsampler`, `detailing_lora`, ...).
- **A pipeline over several models** (LTX `replace`: SAM 2, FLUX.2, ArcFace and LTX) is one served action whose provider resolves each component model from the store; a component's checkpoint is a role named `<model>.<role>`.
